# VeOmni EP+FSDP：一个物流网络的故事

> 本文是 [VeOmni EP+FSDP 深度源码分析](veomni-ep-fsdp-deep-dive.md) 的科普改写版。全文用物流隐喻替代代码和技术术语。零代码，全物流世界观。

## A. TL;DR 故事

一家物流集团想让旗下的通用快递网络支持"专业仓库只存特定品类"的分仓制（Expert Parallelism），同时继续沿用原有的拆箱共享制（FSDP）来节约每个站点（GPU）的仓储空间。他们没有推倒重建整套物流系统，而是对市面上最通用的快递平台进行热插拔改装（monkey-patch），用一张分仓配送单（ParallelPlan）声明哪些货物要按仓号切分、哪些要按货架层切分，再画出两张独立的物流版图（DeviceMesh）——一张管日常配送，一张专管分仓业务。最终，普通货物和专业仓库的货物在同一个网络里各行其道，退货差异单（Gradient）经过对账除数修正后精确归位，整个系统只用十六行配送声明就完成了从通用网络到分仓网络的升级。

## C. 三层解释

### C.1 一句话版

在不拆除现有快递网络的前提下，通过热插拔改装和一张分仓配送单，让每个站点只负责一部分专业仓库，同时用拆箱共享制管理日常库存货物。

### C.2 一段话版

想象一个已经在运转的全国快递网络，每个站点都有完整的仓库。现在业务升级——某些品类的包裹需要专业仓库处理，但不可能在每个站点都建全部品类的专业仓库。于是总部做了三件事：第一，对现有快递平台做热插拔改装，让它识别"专业仓库"这个概念；第二，画两张物流版图，一张管日常配送的拆箱共享，一张管专业仓库之间的干线互发；第三，下发一张分仓配送单，声明哪些货物按仓号切、哪些按货架层切。日常运营时，包裹到达楼层后先经过分拣台，被送往对应的专业仓库，专业仓库处理完再汇总。库存快照和退货差异单则分别走各自版图的规则，互不干扰。

### C.3 技术版

VeOmni 的核心设计是在不修改通用模型定义的前提下，通过热插拔改装（monkey-patch）注入分仓制（Expert Parallelism）能力，并与拆箱共享制（FSDP）协同工作。系统构建两套独立的物流版图（DeviceMesh）：主版图管理数据并行与拆箱共享，分仓版图管理专业仓库之间的干线互发（All-to-All）与各自的拆箱共享。分仓配送单（ParallelPlan）用仓位地址通配符（FQN pattern）声明切分方式——按仓号切分（Shard(0) on expert dim）或按货架层切分（Shard(1) on hidden dim）。拆箱共享制初代路径采用"排除再单独包装"策略：主拆箱先把专业仓库列入免重复入库清单（ignored_states），然后用分仓版图对每个专业仓库单独做拆箱共享。退货差异单（Gradient）的对账除数修正（gradient_postdivide_factor）确保分仓后平均值仍然正确。

## D. 逐章改写

### D.1 全局概览：分仓制遇上拆箱共享制

**结论先行：** VeOmni 没有从零搭建新的物流网络，而是对市面上最通用的快递平台做了一次热插拔改装（monkey-patch），用一张分仓配送单（ParallelPlan）就把分仓制（Expert Parallelism）注入了既有的拆箱共享制（FSDP）体系。

**物流解释：**

物流行业有两种建设思路。一种是自建全链路网络：从站点选址到干线调度到仓库管理系统，全部定制化开发。另一种是在已有的通用网络上做改装：保留原有的仓库布局、配送流程、管理接口，只在关键节点做热插拔，让系统识别新的业务类型。VeOmni 选择了第二条路。它面对的通用平台已经有成熟的仓库结构定义、配送流程和管理接口，数以千计的仓库型号都已经在这个平台上注册。如果推倒重建，意味着所有仓库型号都要重新适配，工程量巨大且维护成本高昂。

热插拔改装的核心动作是：在系统运行之前，把原平台中某些标准模块替换成带有分仓能力的升级模块。这些升级模块保留了原模块的对外接口——进出的包裹格式、与相邻楼层的衔接方式都不变——但内部增加了"把库存货物（Weight/Parameters）按专业仓库维度切分"的能力。这意味着上下游楼层完全感知不到变化发生了，整个网络的宏观行为保持一致。

改装完成后，系统的初始化按严格的四步流程执行。第一步，精度提升——把某些低精度的库存货物升级为更高精度的格式，确保后续计算不会因为精度不足而累积误差。第二步，设置库存快照（Checkpoint）——在关键楼层插入快照点，使得系统在极端情况下可以从快照恢复，而不需要从头开始整个发货出仓（Forward pass）流程。第三步，配置张量并行——这一步与分仓制无关，是通用网络自身的优化手段。第四步，也是最关键的一步，执行分仓制与拆箱共享制的联合部署。这一步会读取分仓配送单，根据声明把对应的库存货物切分到各站点，然后用拆箱共享制包装所有模块。

这四步的顺序不能打乱。精度提升必须在拆箱共享之前完成，因为一旦库存货物被分片到各站点，再做格式转换会导致不一致。库存快照必须在拆箱共享之前设置，因为拆箱共享会改变参数的存储方式，快照系统需要在原始状态下注册。分仓制和拆箱共享制必须同时执行，因为分仓切分决定了哪些货物不参与主拆箱——它们将有自己独立的拆箱流程。整个四步流程在一个入口函数中串行完成，确保了顺序不会被打乱。

| 物流隐喻 | 技术实体 |
|---|---|
| 热插拔改装 | monkey-patch |
| 分仓配送单 | ParallelPlan |
| 分仓制 | Expert Parallelism (EP) |
| 拆箱共享制 | FSDP |
| 通用快递平台 | HuggingFace models |
| 库存快照 | Checkpoint / gradient checkpointing |
| 库存货物 | Weight/Parameters |

**三条要点**：

- 热插拔改装让系统无需重建即可获得分仓能力，所有已注册仓库型号自动兼容。
- 四步初始化流程的严格顺序保证了精度、快照、切分三者之间不产生冲突。
- 与从零定制的方案相比，热插拔路线牺牲了极致灵活性，但换来了对上千种现有仓库型号的即时支持。

### D.2 仓库结构：三维货架的专业仓库

**结论先行：** 升级后的专业仓库把所有货物统一存放在三维货架上——第一维是仓号、第二维和第三维是货架的行列——这种结构使得按仓号切分和批量加工（grouped_gemm）都变得天然可行。

**物流解释：**

在原始的通用快递平台中，每个专业仓库是一个独立的存储单元，拥有自己的库存货物。如果一个楼层有六十四个专业仓库，系统就需要管理六十四份独立的库存记录。这种"一仓一清单"的方式在小规模运营时没有问题，但当需要把不同仓库的货物切分到不同站点时，六十四个独立单元意味着六十四次切分操作，管理复杂度急剧上升。

热插拔改装后的专业仓库采用了一种巧妙的统一存储方案：把所有仓库的库存货物合并到一个三维货架中。第一维表示仓号——第几号专业仓库；第二维和第三维表示这个仓库内部货架的行和列。举个例子，如果有六十四个专业仓库，每个仓库有两种库存货物（入库清单和出库清单各一份），那么整个楼层只需要管理两个三维货架，而不是一百二十八份独立清单。这种合并的代价很小——原始数据本就存在，只是换了一种组织方式——但收益很大：所有涉及"按仓号"操作的逻辑都可以直接在第一维上进行。

三维货架还为批量加工（grouped_gemm）提供了基础。在发货出仓阶段，包裹到达楼层后首先经过分拣台。分拣台的工作分为两步：先对所有包裹计算归属概率，然后取概率最高的若干项，决定每个包裹去哪个专业仓库。分拣台支持两种工作模式。第一种是"逐仓分拣"——依次打开每个仓库的门，把属于这个仓库的包裹送进去处理，再把结果收集起来。这种方式逻辑简单但效率低，因为每次只有一个仓库在工作，其余仓库空闲。第二种是"批量加工"——利用三维货架的结构优势，把所有仓库的工作合并成一次大规模操作，所有仓库同时处理各自的包裹。批量加工的前提正是三维货架：只有当所有仓库的库存货物在物理上连续排列时，合并操作才有可能。

改装过程发生在系统启动阶段。系统扫描原平台的模块注册表，找到所有标注为"专业仓库"或"分拣台"的模块类型，用升级版本替换它们。升级版本继承了原版本的所有对外接口，因此上下游楼层不需要任何适配。替换完成后，系统根据原模块中存储的独立库存货物，自动构建三维货架。整个过程对用户完全透明——从外部看，模型结构没有变化，但内部的存储方式已经为分仓切分做好了准备。值得强调的是，声明一个楼层的分仓方式只需要极少量的配送声明——指明哪些货架按仓号切、哪些按货架层切。这种声明式设计把"做什么"和"怎么做"彻底分离。

| 物流隐喻 | 技术实体 |
|---|---|
| 三维货架 | 3D tensor [num_experts, dim, dim] |
| 仓号（第一维） | expert dimension |
| 分拣台 | Router/Gate |
| 逐仓分拣 | eager mode (per-expert loop) |
| 批量加工 | grouped_gemm (fused Triton kernel) |
| 热插拔改装 | monkey-patch |
| 配送声明 | parallel_plan.py |

**三条要点**：

- 三维货架把六十四份独立库存合并为两个连续结构，使得按仓号切分只需一条声明。
- 分拣台的两种工作模式（逐仓分拣与批量加工）在对外接口上完全一致，切换模式不影响上下游。
- 热插拔改装在系统启动时一次完成，运行时不产生额外开销。

### D.3 物流版图：两张地图的智慧

**结论先行：** 系统需要两张独立的物流版图（DeviceMesh）——主版图管日常配送的拆箱共享，分仓版图管专业仓库之间的干线互发（All-to-All）——因为两套业务对站点分组的逻辑截然不同。

**物流解释：**

为什么不能用一张版图？因为日常配送和分仓业务对"谁和谁是一组"的回答完全不同。日常配送关心的是数据并行——每个站点处理不同批次的包裹，但库存货物相同，所以需要在"持有相同货物的站点"之间做拆箱共享。分仓业务关心的是专业分工——每个站点只持有部分仓库，所以需要在"持有不同仓库的站点"之间做干线互发。这两种分组逻辑在同一组站点上形成不同的切分维度，一张版图无法同时表达两种正交的分组关系。

主版图最多有六个维度，涵盖了分段中转并行、数据复制并行、数据切片并行、长序列并行、上下文并行和张量并行。这张版图是通用网络自带的，VeOmni 不需要修改它。分仓版图则是 VeOmni 新增的，它只有两个维度：分仓维和分仓拆箱维。分仓维把站点按"你负责哪些专业仓库"分组——同一组内的站点持有不同仓库，需要通过干线互发交换包裹。分仓拆箱维把站点按"你和谁共享同一个仓库的拆箱"分组——同一组内的站点持有同一个仓库的不同分片，需要在发货出仓前合并清单（All-Gather）拼回完整的库存货物。

两个维度在物理站点上的排列方式决定了通信效率，这引出了两种布局策略。第一种叫就近分仓（ep_inside）：把同一个分仓组的站点安排在物理上相邻的位置——比如同一台机器的不同卡槽。这样干线互发走的是站点之间最快的内部通道，延迟极低。代价是分仓拆箱维的站点分散在不同机器上，合并清单需要走跨机器的较慢通道。第二种叫跨区分仓（ep_outside）：把同一个分仓组的站点分散到不同机器上，干线互发走跨机器通道，但分仓拆箱维的站点则集中在同一台机器上，合并清单走快速内部通道。选择哪种布局取决于业务特征：如果干线互发的数据量远大于合并清单，就近分仓更优；反之则跨区分仓更优。

以十六个站点为例，分仓规模为四、分仓拆箱规模为四。就近分仓布局下，站点零到三构成一个分仓组，它们在物理上相邻，共享高速内部通道。站点零还和站点四、八、十二构成一个拆箱组，它们分散在四台机器上。跨区分仓布局下则正好反转：站点零和四、八、十二构成分仓组（跨机器干线互发），站点零到三构成拆箱组（本机合并清单）。从分仓版图中提取子版图时，系统使用扁平化操作把多维版图压缩到一维，再按需切出承运合同分组（ProcessGroup）。每个承运合同分组定义了一组站点之间的通信契约：哪些站点之间可以互发、用什么协议、走什么通道。

退货差异单（Gradient）的对账需要特别注意。在纯拆箱共享制下，对账除数等于参与拆箱的站点数量——多少个站点共同持有一份货物的分片，退货差异单就除以多少。但分仓制引入后，全局站点数可能远大于拆箱组的站点数。系统通过一个显式的对账除数修正来确保退货差异单的平均值在全局范围内正确。具体规则是：对账除数等于全局站点数。当前版本要求张量并行和分段中转并行的规模都为一，这是因为对账除数修正的公式在多种并行方式叠加时会变得复杂，暂时只支持最简洁的配置。

| 物流隐喻 | 技术实体 |
|---|---|
| 主版图 | main DeviceMesh [pp, dp_replicate, dp_shard, ulysses, cp, tp] |
| 分仓版图 | ep_fsdp mesh (2D: ep, ep_fsdp) |
| 就近分仓 | ep_inside layout |
| 跨区分仓 | ep_outside layout |
| 干线互发 | All-to-All |
| 合并清单 | All-Gather |
| 承运合同分组 | ProcessGroup |
| 对账除数修正 | gradient_postdivide_factor |

**三条要点**：

- 两张版图独立存在，因为日常配送和分仓业务的站点分组逻辑正交，不可混用。
- 就近分仓让干线互发走高速内部通道，跨区分仓让合并清单走高速内部通道——选择取决于哪种通信量更大。
- 对账除数修正是分仓制引入后必须做的数学校正，否则退货差异单的全局平均值会偏离正确值。

### D.4 分仓配送单：从声明到执行

**结论先行：** 分仓配送单（ParallelPlan）是一份纯声明式的文件——它只说"什么货物按什么维度切"，不涉及任何执行细节——而从声明到实际切分需要经过"贴标签、重新分配、撕标签"三步转换。

**物流解释：**

分仓配送单的核心是一个映射关系：仓位地址通配符（FQN pattern）指向切分方式。仓位地址通配符用通配规则匹配仓库中某一类货物的完整路径名。比如，一条通配规则可以匹配"所有楼层中所有专业仓库的入库清单"，另一条可以匹配"所有楼层中所有专业仓库的出库清单"。匹配成功后，配送单告诉系统：这批货物要按仓号切分（按仓号切分，即沿第一维切开，每个站点只拿自己负责的仓号对应的切片）或按货架层切分（按货架层切分，即沿第二维切开，每个站点拿所有仓号但只拿部分列）。通配规则的匹配采用正则表达式——星号表示任意楼层、任意仓号——这使得一条规则可以覆盖整个网络中数百个同类货物。

从声明到执行的三步转换是分仓配送单最精妙的机制。第一步"贴标签"：把站点本地的普通货物包装成物流标签件（DTensor），标注为"同款备货（Replicate）"——这意味着暂时告诉系统"这份货物在所有站点上都有完整拷贝"。这是一个逻辑上的声明，不涉及数据移动。第二步"重新分配"：调用重分布操作，把标签从"同款备货"改为"按仓号切分"或"按货架层切分"。这一步系统会检查实际数据分布与目标分布是否一致。如果站点本地持有的数据恰好就是它应该持有的那个切片，则不产生任何通信——这在大多数初始化场景中成立，因为系统在加载库存货物时就已经按预期做了分片。如果不一致，系统会自动触发站点间的数据搬运。第三步"撕标签"：把物流标签件还原为普通的本地货物，去掉标签系统的元数据开销。此后这份货物在本站点看来就是一份普通的库存，但它实际上只包含属于本站点的那个切片。

除了声明切分方式，分仓配送单还承担了两个关键的信息管理职责。第一个是生成分仓标签（SpecInfo）。在三步转换过程中，系统会为每一份被切分的货物创建一个分仓标签，记录三件事：这份货物归属于哪个分仓版图、它的切分方式是什么、它的完整仓位地址是什么。这些标签在后续的库存快照保存和加载时至关重要——当系统从快照恢复时，需要知道每份货物的切分方式才能正确地拼回或重新切分。第二个职责是生成免重复入库清单。系统遍历所有被分仓配送单标记的货物，找出它们所属的模块，然后告诉主拆箱共享制："这些模块里的货物你不要管，它们有自己独立的拆箱流程。"这个清单是分仓制与拆箱共享制协同工作的关键接口——没有它，主拆箱共享制会试图切分已经被分仓切分的货物，导致双重切分错误。

通配规则的匹配算法值得单独说明。系统不使用简单的字符串前缀匹配，而是把通配符中的星号转换为正则表达式的"匹配任意字符"模式。这意味着通配符可以精确匹配任意深度的嵌套路径。比如，一条通配规则可以匹配"第三楼层的第七号专业仓库的入库清单"和"第十二楼层的第二十号专业仓库的入库清单"，但不会误匹配"第三楼层的分拣台的权重"。这种精确匹配确保了分仓配送单的声明不会波及到不应被切分的货物。当通配规则写得太宽泛时，系统会在初始化阶段就报错，而不是在运行时产生难以诊断的静默错误。

| 物流隐喻 | 技术实体 |
|---|---|
| 分仓配送单 | ParallelPlan |
| 仓位地址通配符 | FQN pattern |
| 按仓号切分 | Shard(0) on expert dim |
| 按货架层切分 | Shard(1) on hidden dim |
| 物流标签件 | DTensor |
| 同款备货 | Replicate placement |
| 分仓标签 | SpecInfo |
| 免重复入库清单 | ignored_states |

**三条要点**：

- 三步转换（贴标签→重新分配→撕标签）保证了在大多数场景下零数据搬运完成切分。
- 分仓标签为库存快照的保存和恢复提供了必要的元数据，没有它快照系统无法识别切分方式。
- 免重复入库清单是分仓制与拆箱共享制之间的边界契约，防止货物被双重切分。

### D.5 第一条路线：拆箱共享制初代的分仓集成

**结论先行：** 拆箱共享制初代路径采用"排除再单独包装"策略——先让主拆箱共享制跳过所有专业仓库，再用分仓版图对每个专业仓库单独做拆箱共享——这种两阶段策略虽然不够优雅，但逻辑清晰且可靠。

**物流解释：**

理解这条路线需要先理解拆箱共享制的基本工作方式。拆箱共享制的核心思想是：库存货物太大，单个站点存不下完整的一份，所以把它拆成若干分片，每个站点只存一个分片。发货出仓时，站点需要临时向其他站点借回缺失的分片，拼成完整货物使用，用完后立刻归还（只保留自己那个分片）。回传回执（Backward pass）时，每个站点计算出的退货差异单也是完整的，但只保留属于自己分片的那部分，其余丢弃。这种"拆着存、拼着用、算完再拆"的循环就是拆箱共享制的日常运转。

问题出在分仓制引入后。专业仓库的库存货物已经被分仓配送单按仓号切分了——站点零只持有仓库零到十五的货物，站点一只持有仓库十六到三十一的货物。如果主拆箱共享制不加区分地把所有货物都纳入管理，它会尝试对已经按仓号切分的货物再做一次拆箱切分。这就像一件已经被分仓切成四份的货物，又被拆箱制再切一次——最终每个站点只拿到原始货物的十六分之一，完全无法正确使用。

"排除再单独包装"策略正是为了避免这种双重切分。第一阶段，系统从分仓配送单中提取免重复入库清单，列出所有已被分仓切分的模块。然后初始化主拆箱共享制时，明确告知它："这些模块里的货物你跳过，不要碰。"主拆箱共享制收到清单后，会在遍历模型结构时主动忽略这些模块的所有参数，只对其余普通模块执行拆箱切分。第二阶段，系统遍历每一个被排除的专业仓库模块，用分仓版图中的分仓拆箱子版图对其单独做拆箱共享。这里有一个关键判断：如果分仓拆箱维的规模为一——即每个专业仓库只有一个站点负责，不存在跨站点的分片——则采用不切分模式，库存货物完整保留在本地。否则采用全切分模式，把专业仓库的货物在分仓拆箱组内再做一次拆箱共享。

对账除数修正是这条路线中最容易出错的环节。在纯拆箱共享制下，退货差异单的对账由拆箱共享制自动完成：它知道有多少个站点参与了拆箱，就自动除以那个数。但分仓制引入后，专业仓库的退货差异单只在分仓拆箱组内对账——比如四个站点——而全局有十六个站点。如果不做修正，专业仓库的退货差异单会比普通模块的大四倍（因为只除以了四而不是十六）。修正方法是在专业仓库的拆箱共享配置中显式地把对账除数再乘以分仓规模。这样最终效果是：退货差异单先在分仓拆箱组内做对账后分摊（Reduce-Scatter），除以分仓拆箱规模；然后对账除数修正再额外除以分仓规模；两次除法的乘积等于全局站点数，对账正确。这条路线最后还注册了两个扩展：一个是库存快照扩展，确保保存和加载时能正确处理分仓切分的货物；另一个是退货差异单裁剪扩展，在裁剪全局退货差异单范数时，能跨主版图和分仓版图正确汇总所有参数的范数值。

| 物流隐喻 | 技术实体 |
|---|---|
| 排除再单独包装 | exclude-then-wrap-separately 方案 |
| 免重复入库清单 | ignored_states |
| 主拆箱共享制 | main FSDP wrapping |
| 分仓拆箱子版图 | ep_fsdp sub-mesh |
| 不切分模式 | NO_SHARD |
| 全切分模式 | FULL_SHARD |
| 对账除数修正 | _gradient_postdivide_factor *= ep_size |
| 对账后分摊 | Reduce-Scatter |
| 退货差异单裁剪 | clip_grad_norm_ |

**三条要点**：

- "排除再单独包装"是分仓制与拆箱共享制初代协作的唯一可靠路径，因为初代接口不支持同一模型中混合不同版图的拆箱。
- 对账除数修正必须精确等于分仓规模，否则专业仓库的退货差异单在全局尺度上数值偏大，导致训练不稳定。
- 分仓拆箱维规模为一时自动退化为不切分模式，这是一个重要的边界情况——它意味着每个站点独立持有完整的专业仓库货物，不需要跨站点借还。

### D.6 第二条路线：拆箱共享制二代的正交切分

**结论先行**：拆箱共享制二代通过四步编排——提取楼层清单、执行分仓制切分、构造双套拆箱配置（标准版图 vs 分仓拆箱版图）、内层-外层双重包装——实现了分仓制与拆箱共享制的正交切分，其中按仓号切分负责专业仓库编号维度，按货架层切分负责隐藏层维度，两把刀方向垂直、互不干扰。

**物流解释**：

想象总调度员拿到一座大楼的蓝图，需要把每个楼层的工具安排到分散在各站点上的仓库中。第一步是翻阅蓝图，找出所有需要单独管理的楼层——哪些楼层有专业仓库、哪些只有普通货物。系统从模型的标准属性中读取"不可拆分楼层"列表，生成一张"楼层名-楼层模块"的清单。这份清单是后续所有操作的基础：有了它，系统才知道一共要处理多少个楼层，每个楼层里有没有专业仓库。

第二步是执行分仓制。系统从模型上取出分仓方案（十六行左右的切分声明），然后调用方案的执行功能。执行过程把每个专业仓库的工具转成物流标签件，沿仓库编号维度（维度 0）切开，每个站点只保留自己负责的那部分仓库的工具。切完后，工具被从物流标签件转回普通格式——因为接下来拆箱共享制二代会用另一张版图重新给它们贴标签。这里有一个关键设计：执行结果被挂载到模型上作为一份"切分档案"，记录了每个参数的切分方式和维度信息，供后续保存库存快照时使用。同时，系统还从方案中提取了一份"免重复入库清单"——所有需要独立管理的专业仓库模块的位置映射。

第三步是构造两套不同的拆箱配置。**标准拆箱配置**使用普通的拆箱共享版图，管理所有非专业仓库的工具——注意力模块、归一化层、分拣台等等。它的切分方向是默认的维度 0。**专业仓库拆箱配置**则使用分仓拆箱版图中的"拆箱组"子网格，专门管理已经被分仓制切过的专业仓库工具。这套配置有一个核心设定：切分方向指令被强制设为按货架层切分。为什么？因为仓库编号维度（维度 0）已经被分仓制占用了。如果拆箱共享制还在同一个维度上再切一刀，每个站点就只剩下极少数仓库的极小碎片——仓库编号被切两次之后，批量加工的累计分界线无法正确标记每个仓库的包裹边界，整个加工链路就断裂了。沿维度 1 切，则完全避开了这个冲突：分仓制切"哪些仓库归我"，拆箱共享制切"每个仓库的工具我存哪一半"。

举一个数值例子来说明正交切分的效果。假设某个专业仓库的工具原始形状是 128 个仓库、每个工具 4096 行、2048 列。分仓数为 4，分仓制沿维度 0 切分后，每个站点持有 32 个仓库的工具，形状变为 32 乘以 4096 乘以 2048。如果拆箱组有 8 个站点，拆箱共享制二代沿维度 1 切分，每个站点最终持有的工具形状是 32 乘以 512 乘以 2048——4096 除以 8 等于 512。两次切分发生在完全不同的维度上，互不影响。发货出仓时，拆箱共享制二代自动执行合并清单，将维度 1 上的碎片还原为完整的 4096，然后批量加工才能在正确的工具形状上运行。

第四步是包装，顺序极为关键：先包内层、再包外层。对于每个包含专业仓库的楼层，系统先用专业仓库拆箱配置把仓库模块包起来（内层），然后再用标准拆箱配置把整个楼层包起来（外层）。拆箱共享制二代是递归识别的——当它在处理整个楼层时发现某个子模块已经被包装过，就自动跳过该子模块的参数，不做重复切分。这就是"免重复入库"的机制：不需要手动列清单（这是和一代的一个区别），框架自动识别已有管家。每个楼层包装完后，系统记录下这个楼层内部包含了哪些独立的拆箱单元——专业仓库一个单元、精度豁免模块（如有）一个单元、楼层整体一个单元。这份记录用于后续的提前备货：当前楼层发货出仓完成时，系统根据这份清单提前执行下一个楼层的合并清单操作，让通信和计算重叠起来。

还有一个容易忽略的细节：对账除数修正。专业仓库的拆箱共享制只在拆箱组内做对账后分摊，而实际需要在所有数据并行站点上取平均值。系统通过显式设置对账除数为全网站点总数来补偿这个差异。如果不做修正，专业仓库的退货差异单只会被拆箱组的站点数除过一次，而普通工具的退货差异单被全部数据并行站点数除过——两者的缩放比例不一致，训练就会偏移。

提前备货链的设计也值得展开。当分仓制启用时，标准的隐式提前备货会被干线互发的同步操作阻塞——站点需要等待远程数据到达才能继续。系统因此切换到显式提前备货模式：在当前楼层发货出仓结束时，主动触发下一个楼层所有拆箱单元的合并清单。备货顺序是反向遍历单元列表——先备楼层整体的参数（注意力、归一化），再备精度豁免模块，最后备专业仓库的工具。回传回执（反向计算）时，备货方向反过来：当前楼层回传完毕后，提前备好上一个楼层的拆箱单元。这样，不管是发货出仓还是回传回执，通信都能和计算并行进行。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 标准拆箱配置 | fsdp_kwargs (mesh=fsdp_mesh) |
| 专业仓库拆箱配置 | expert_fsdp_kwargs (mesh=ep_fsdp_mesh, Shard(1)) |
| 切分方向指令 | shard_placement_fn |
| 按仓号切分 | Shard(0)，沿专家维度 |
| 按货架层切分 | Shard(1)，沿隐藏层维度 |
| 对账除数修正 | set_gradient_divide_factor(world_size) |
| 提前备货链 | set_modules_to_forward/backward_prefetch |
| 楼层内拆箱单元清单 | _fsdp_modules 列表 |

**三条要点**：

- 按仓号切分（分仓制）和按货架层切分（拆箱共享制二代）方向正交——仓库编号维度和隐藏层维度各切一刀，互不干扰，避免了累计分界线失效的致命问题
- 内层先包、外层后包的顺序让框架自动识别已有管家，无需手动编写免重复入库清单，比一代路径更简洁
- 对账除数必须手动修正为全网站点总数，否则专业仓库和普通工具的退货差异单缩放比例不一致，训练会偏移

### D.7 发车派送全流程：从分拣到送达再回程

**结论先行**：分仓制下的发货出仓经历五个阶段——构造分拣掩码、预处理计算发送接收清单、包裹编号重排加干线互发加分区重排、批量加工、以及逆向分区重排加逆向干线互发加还原编号的加权累加——形成一条完整的"分拣-派送-加工-回收"作业链。

**物流解释**：

把这条作业链想象成一个快递枢纽的日常操作。每天早上，大量包裹涌入枢纽，每个包裹上贴着"请送到第 X、第 Y、第 Z 个专业仓库"的标签（这就是分拣台的路由结果）。枢纽需要做的事情是：先搞清楚每个仓库该收多少包裹，然后把包裹实际发出去，让各仓库加工完毕后把结果收回来。问题在于，这些专业仓库分散在不同城市的站点上，需要跨站通信才能完成派送和回收。

**第一阶段：构造分拣掩码**。系统把路由结果转化为一张三维的分拣掩码表——维度分别是仓库编号、选择序号、包裹编号。掩码中的每个值标记"这个包裹是否被分配给了这个仓库"。为什么需要这张表？因为后续所有操作——统计、排序、加权——都依赖这张表来定位每个包裹和每个仓库的对应关系。

**第二阶段：预处理**。这是调度层面最复杂的阶段。系统先在分拣掩码上做求和，得到每个仓库在本站收到了多少个包裹——比如仓库 0 收到了 10 个、仓库 1 收到了 5 个。然后把这些计数按站点分组求和，得到"发送清单"：当前站点要发给站点 0 的包裹总数是 300 个、发给站点 1 的是 280 个。但光知道"我要发多少"不够，还需要知道"我要收多少"。系统通过一次合并清单操作，把所有站点的计数信息汇总起来。每个站点从汇总结果中提取自己负责的仓库的信息：各个站点分别要发给我多少包裹？求和后得到"接收清单"。发送清单和接收清单是干线互发操作的必要输入——没有它们，通信原语不知道该分配多大的接收缓冲区。

**第三阶段：包裹编号重排、干线互发、分区重排**。这个阶段分三步。第一步是包裹编号重排：把包裹从原始顺序重新排列成按仓库编号聚拢的顺序。具体做法是用分拣掩码做遮罩选择——对每个仓库，从所有包裹中选出分配给该仓库的那些，按仓库编号依次拼接。排列后的顺序是"仓库 0 的包裹、仓库 1 的包裹、仓库 2 的包裹..."，同时记录下原始位置的索引，用于回程时还原。

第二步是干线互发：按照发送清单和接收清单，各站点之间交换包裹。站点 0 把要发给站点 1 的包裹发出去，同时从站点 1 接收发给自己的包裹。干线互发完成后，每个站点手里拿到的是所有站点发来的、目的地是本站专业仓库的包裹。

但有一个布局问题：干线互发后的包裹排列是"交错"的——来自站点 0 的给仓库 0 的包裹、来自站点 0 的给仓库 1 的包裹、来自站点 1 的给仓库 0 的包裹、来自站点 1 的给仓库 1 的包裹...同一个仓库的包裹分散在多个不连续的区块中。第三步的分区重排就是把这种交错布局变成分块布局——把仓库 0 来自所有站点的包裹合并到一起、仓库 1 的合并到一起...这样每个仓库的包裹形成一个连续的区块，批量加工才能高效运行。分区重排通过一个转置索引实现：把一张"站点数 x 本地仓库数"的矩阵做转置再展平，得到重排顺序。

**第四阶段：批量加工**。包裹按仓库分好块后，系统计算每个仓库的累计分界线——前 k 个仓库一共有多少包裹——作为划分子矩阵的边界标记。然后调用三次批量加工（一次门控投影、一次上行投影、一次下行投影），中间夹着双通道加工的激活操作。具体细节留到 D.9 节展开。

**第五阶段：逆向全流程**。加工完成后，结果需要原路返回。系统先做逆向分区重排——用一个反向的转置索引把分块布局恢复成交错布局。然后执行逆向干线互发——发送清单和接收清单互换位置，把结果发回原始站点。最后做还原编号的加权累加：用之前记录的原始位置索引，把每个包裹的加工结果放回原始位置，同时乘以分拣台给出的路由权重，对同一个包裹被多个仓库处理的结果做加权求和。加权累加的实现很巧妙：先用遮罩选择从路由权重矩阵中提取有效权重，给每个结果乘上对应权重，然后用散列累加操作把加权后的结果原子地加到输出的正确位置上。之所以用散列累加而非简单赋值，是因为一个包裹可能被多个仓库处理过，多个结果需要累加到同一个输出位置。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 分拣掩码 | expert_mask [num_experts, top_k, num_tokens] |
| 发送清单 | input_splits [ep_size] |
| 接收清单 | output_splits [ep_size] |
| 包裹编号重排 | permute（masked_select + index_select） |
| 干线互发 | all_to_all |
| 交错布局 | 按来源站点排列（interleaved layout） |
| 分块布局 | 按仓库编号排列（blocked layout） |
| 分区重排 | sort_chunks_by_idxs |
| 还原编号的加权累加 | unpermute（scatter_add_ + routing weights） |

**三条要点**：

- 干线互发后的交错布局必须经过分区重排变成分块布局，否则同一仓库的包裹不连续，批量加工无法正确划分子矩阵边界
- 逆向全流程是正向的精确镜像：逆向分区重排、互换清单的逆向干线互发、加权散列累加，每一步都是正向操作的逆运算
- 加权累加用散列累加而非赋值，因为一个包裹可能被多个仓库处理过，多个结果需要原子累加到同一输出位置

### D.8 干线互发：自动反向的对称通信

**结论先行**：干线互发通过自定义的自动求导封装实现，回传回执时自动交换发送清单和接收清单、执行一次反方向的干线互发——正向和反向操作具有完美的数学对称性，同时提供同步和异步两种模式。

**物流解释**：

干线互发是整条作业链中最关键的通信操作——它负责把包裹从生产站点运送到加工站点，又在回程中把结果运送回来。在物流世界观里，干线互发就像一个城际快递网：每个城市的枢纽既有要发出去的包裹，也有要接收的包裹，所有城市同时交换，一轮通信完成全部的收发。

封装的核心在于自动求导。系统把干线互发操作包装成一个支持自动求导的运算单元——正向运算时记住两份关键信息：发送清单（我给每个站点发了多少包裹）和接收清单（我从每个站点收了多少包裹）。反向运算时，这两份清单自动互换。

为什么互换就够了？因为干线互发的数学性质决定了这一点。正向时，站点 A 按发送清单把 300 个包裹发给站点 B，同时按接收清单从站点 B 接收 290 个包裹。回传回执时，退货差异单需要沿相反方向流动：站点 A 需要把自己收到的 290 个包裹对应的退货差异发回站点 B，同时从站点 B 接收 300 个包裹对应的退货差异。这恰好就是一次"发送清单=原来的接收清单、接收清单=原来的发送清单"的干线互发。系统不需要发明任何新的通信原语——反向的干线互发就是参数交换后的正向干线互发，直接递归调用自身即可。

正向操作的实现有几个工程细节值得注意。首先是短路优化：如果只有一个站点（没有分仓制），直接返回输入，完全跳过通信。其次是内存连续性保证：通信原语要求输入数据在内存中连续排列，系统在通信前强制做一次连续化操作。第三是输出缓冲区的预分配：根据接收清单的总和，提前分配恰好大小的接收缓冲区。缓冲区大小等于接收清单之和乘以每个包裹的特征维度——不多分配一个字节，也不少分配一个字节。

异步模式是同步模式的升级版。区别在于通信操作不等待完成就立即返回，同时返回一张存根票据。调用方需要在恰当的时机手动等待这张票据，确认通信已完成后才能读取接收到的数据。异步模式的价值在于通信-计算重叠：在等待干线互发完成的同时，站点可以执行其他计算任务，而不是干等着。不过在当前的实现中，主路径使用的是同步模式——异步模式作为备选接口保留。

与其他框架的对比揭示了一个有趣的设计取舍。有些框架在干线互发之前会做对齐填充——确保每个仓库接收的包裹数量是某个对齐值的倍数（比如 8 或 16 或 32），因为底层的矩阵乘法内核对对齐的输入运行更快。当前系统不做对齐填充，因为它使用的批量加工内核能在内部自行处理不对齐的包裹数量。这意味着上层代码更简洁（不需要额外的填充和去填充逻辑），但对底层内核的灵活性要求更高。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 干线互发 | All-to-All (dist.all_to_all_single) |
| 自动求导封装 | torch.autograd.Function |
| 发送清单 | input_split_sizes |
| 接收清单 | output_split_sizes |
| 清单互换 | backward 中交换 input/output split sizes |
| 短路优化 | world_size == 1 时直接返回 |
| 存根票据（异步模式） | async_handle（需手动 wait） |
| 对齐填充（本系统不做） | TOKEN_GROUP_ALIGN_SIZE_M 对齐 |

**三条要点**：

- 干线互发的反向操作就是清单互换后的正向操作——这种完美对称性意味着不需要任何额外的通信原语，反向递归调用正向即可
- 同步模式等待通信完成后返回数据，异步模式立即返回并附带存根票据，调用方按需等待——后者支持通信与计算重叠
- 本系统不做对齐填充，由底层批量加工内核自行处理不对齐的包裹数量，换来上层代码的简洁性

### D.9 批量加工：双通道融合计算

**结论先行**：批量加工通过自定义自动求导封装，将双通道加工的前向（三次批量加工加激活）和反向（交替使用两种不同规格的批量加工分别计算包裹退货差异和工具校正差异，加上激活函数的重计算）融合为高效的运算序列，反向计算量约为前向的三倍。

**物流解释**：

批量加工是作业链的计算核心——包裹经过分拣、派送、分区重排之后，终于到达了专业仓库，现在要被实际加工。每个仓库收到的包裹数量不同（有的仓库热门收到很多，有的冷门只收到几个），但所有仓库使用的工具规格相同（工具的行数和列数一致）。批量加工的精髓在于：把所有仓库的加工任务打包成一次调用，而非逐个仓库循环处理。

**前向：三次加工加双通道激活**。每个专业仓库有三套工具：门控投影工具、上行投影工具、下行投影工具。加工过程是：先用门控工具对包裹做第一次加工，得到门控结果；同时用上行工具做第二次加工，得到上行结果。然后对门控结果做一次激活变换（让信号通过一个 S 形门控），再与上行结果逐位相乘——这就是"双通道加工"的含义：两条通道并行计算后合并。合并结果再用下行工具做第三次加工，得到最终输出。三次加工都使用同一种批量加工模式：所有仓库的工具规格（行列数）相同，但每个仓库处理的包裹数量不同。

累计分界线在这里扮演了关键角色。它是一组递增的数字，标记了每个仓库的包裹在总序列中的结束位置——比如仓库 0 的包裹占据位置 0 到 110、仓库 1 占据 110 到 230、仓库 2 占据 230 到 330。批量加工内核根据这组分界线，把总包裹序列切成多段子矩阵，每段用对应仓库的工具进行矩阵乘法。所有子矩阵的乘法在一次内核调用中并行完成，避免了逐仓库循环的调度开销。

前向结束时，系统保存七项信息用于反向：输入包裹、累计分界线、三套工具、以及门控投影的输出（注意：是激活变换之前的输出，不是之后的）和上行投影的输出。为什么保存激活变换之前的值？因为反向需要的是激活函数对原始输入的导数，而非对输出的导数。同时，激活变换之后的结果（门控激活值）不保存而是在反向中重新计算——这是经典的时间-空间权衡：多花一次激活计算的时间，换来一整块中间结果的内存节省。

**反向：两种规格的批量加工交替使用**。反向计算要回答两个问题：包裹的退货差异是多少（包裹退货差异，用于向上游传递退货差异），以及每套工具该如何校正（工具校正差异，用于更新工具参数）。两个问题用到的批量加工规格不同。

计算包裹退货差异时，使用的是"工具规格统一"的批量加工——和前向一样，所有仓库的工具行列数相同，变化的是每个仓库的包裹数量。数学上，这是拿退货差异单乘以工具矩阵来反推输入应有的退货差异。

计算工具校正差异时，使用的是另一种规格——"工具规格统一"但变化维度从包裹数量换成了缩减维度。具体来说，这种批量加工把包裹数量作为缩减维度（矩阵乘法的 K 维），工具形状的两个维度（行数和列数）是所有仓库共享的。这是因为工具校正差异的计算方式是"转置的激活值乘以输入"，其中包裹数量变成了求和缩减的维度。

双通道加工的反向尤其复杂，需要处理两条分支。回传的退货差异单先经过下行工具反推，得到合并层的退货差异。然后分成两条路：对上行通道，退货差异等于合并层退货差异乘以门控激活值（因为前向是逐位相乘，所以反向用另一个乘数作为系数）；对门控通道，退货差异等于合并层退货差异乘以上行通道的输出。门控通道的退货差异还需要再经过激活函数的反向操作——这一步需要用到之前保存的门控投影原始输出（激活前的值），系统在此时重新计算一次激活变换来获得激活后的值。

两条分支各自独立地计算包裹退货差异和工具校正差异（每条分支各一次包裹退货差异计算、一次工具校正差异计算），最后把两条分支的包裹退货差异相加——因为原始包裹同时被两条通道使用，退货差异需要从两条路径累加。

统计一下反向的运算量：三次包裹退货差异计算（下行反推、门控分支反推、上行分支反推）加三次工具校正差异计算（下行工具校正、门控工具校正、上行工具校正），再加上一次激活重计算、一次激活反向、三次逐位乘法和一次逐位加法。相比前向的三次批量加工加一次激活加一次逐位乘法，反向的计算量约为前向的三倍。这符合深度学习训练中"反向约为前向二到三倍"的经验法则——因为反向既要算包裹退货差异（和前向等量），又要算工具校正差异（额外增加同等量级的计算）。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 批量加工（工具规格统一，包裹数变化） | group_gemm_same_nk（前向 + dgrad） |
| 批量加工（工具规格统一，缩减维度变化） | group_gemm_same_mn（wgrad） |
| 累计分界线 | cumsum [num_local_experts] |
| 双通道加工 | SwiGLU（silu(gate) * up） |
| 门控投影/上行投影/下行投影 | gate_proj / up_proj / down_proj |
| 包裹退货差异 | dgrad（数据梯度） |
| 工具校正差异 | wgrad（权重梯度） |
| 激活重计算 | 反向中重新调用 silu，不保存 silu 后的结果 |
| 时间-空间权衡 | 多花一次计算换来一块中间结果的内存节省 |

**三条要点**：

- 两种批量加工规格的区别在于"谁变化"：计算包裹退货差异时每个仓库的包裹数量变化（累计分界线标记包裹维度），计算工具校正差异时包裹数量变成缩减维度（累计分界线标记缩减维度）
- 前向保存激活变换前的输出、反向重计算激活变换后的值，这个时间-空间权衡用一次廉价计算换来一整块中间结果的内存节省
- 双通道加工的反向产生两条分支，各自独立计算包裹退货差异和工具校正差异后，两条分支的包裹退货差异相加——因为原始包裹同时进入了两条通道

### D.10 回传回执与对账：退货差异单的全局同步

**结论先行**：回传回执阶段的干线互发是发货出仓阶段的镜像操作，但退货差异单的对账除数需要人工修正——因为专业仓库的拆箱共享组只有全网站点的四分之一，不修正的话对账结果相当于只看了局部账目。

**物流解释**：

发货出仓阶段的干线互发把包裹从源站点送到目标专业仓库，回传回执阶段需要把退货差异单沿原路送回。这个反向过程有一个优雅的对称性——发车时每个站点按目的地拆分包裹并互发，回传时只需把拆分规则互换。站点 A 原本发了 30 个包裹给站点 B、收了 50 个包裹从站点 B 来；现在退货差异单反过来，站点 A 把 50 份差异单发回给站点 B、从站点 B 收回 30 份。拆分数量互换，通信原语不变。

真正的难题在退货差异单的对账除数。全网 16 个站点训练同一批数据，最终每个库存货物（参数）的退货差异单应该是全部 16 个站点差异单之和除以 16。对于普通货物（注意力层等），拆箱共享制的对账后分摊操作自动覆盖全部 16 个站点，除以 16，结果正确。但专业仓库的情况不同：分仓制把 128 个专业仓库分给 4 组站点，每组 4 个站点。专业仓库 E0 到 E31 只在站点 {0, 4, 8, 12} 上存在——它们的退货差异单只在这 4 个站点之间做对账后分摊，系统自动除以 4。问题是 4 不等于 16。4 个站点只处理了全网数据的四分之一，正确的对账除数应该是 16（等于全网站点数），否则退货差异单被低估了四倍。

修正方法因路径不同而异。第一条路径下，系统在拆箱共享制包装完成后，直接将对账除数修正为原始值乘以分仓组数（即 4 乘以 4 等于 16）。第二条路径下，系统通过公开接口直接设定对账除数为全网站点数 16。两种做法殊途同归：确保专业仓库的退货差异单与普通货物一样，以全网站点数为分母。

退货差异单封顶（退货差异单裁剪）同样需要分仓感知。普通货物的差异单范数可以在全网站点上一次性合并得到。但专业仓库的差异单分布在两个维度上——同一组专业仓库的拆箱切片散在拆箱共享组内，不同组专业仓库散在分仓组内。因此需要两步合并：第一步在拆箱共享组内合并（收集同一批仓库工具各切片的差异单范数），第二步在分仓组内合并（收集不同仓库的差异单范数）。两步合起来才得到全网差异单的全局范数，用于统一封顶。

第二条路径对此做了进一步抽象：用一个通用的多步合并函数，接受一组承运合同分组的列表，按顺序逐个执行合并。普通货物传入一个分组（全网拆箱共享组），专业仓库传入两个分组（拆箱共享组加分仓组），统一接口处理了两种情况。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 退货差异单 | 梯度（Gradient） |
| 对账除数修正 | gradient_divide_factor 修正 |
| 对账后分摊 | Reduce-Scatter |
| 退货差异单封顶 | clip_grad_norm |
| 两步合并 | 两阶段 all-reduce（ep_fsdp_group + ep_group） |
| 承运合同分组列表 | reduce_groups 参数 |

**三条要点**：

- 回传回执的干线互发是发货出仓的精确镜像——拆分规则互换，通信原语不变
- 专业仓库的对账除数必须从拆箱共享组大小修正为全网站点数，否则退货差异单被低估
- 退货差异单封顶需要两步合并——先在拆箱共享组内合并切片，再在分仓组间合并不同仓库

### D.11 提前备货：跨版图的预取调度

**结论先行**：分仓制使每个楼层内部产生多个独立的拆箱共享单元，隐式的提前备货链因此断裂，必须手动建立跨版图的备货清单才能让通信与加工重叠。

**物流解释**：

没有分仓制的普通楼层只有一个拆箱共享单元。当楼层 N 完成加工时，拆箱共享制自动在传送带上安排"给楼层 N+1 提前备货"的任务——从各站点收集下一楼层的工具切片。因为只有一个单元，系统知道"下一个备货对象是谁"，隐式调度自然生效。

但分仓制打破了这种简单性。一个 MoE 楼层内部至少有两个拆箱共享单元：专业仓库在分仓拆箱版图上独立包装成一个单元，整个楼层在普通版图上包装成另一个单元。如果还有需要高精度运算的分拣台模块，那就是三个单元。问题是：拆箱共享制的隐式备货只能感知同级别的下一个单元。楼层 N 的外层单元（整个楼层）完成后，系统不知道楼层 N+1 内部还有一个内层单元（专业仓库）需要提前备货。结果是专业仓库的工具收集（合并清单操作）只能在真正需要时才发起，错过了与上一楼层加工重叠的窗口。传送带上出现空转——上一楼层加工已结束，下一楼层工具还没到位。

解决方案是为每个楼层维护一份完整的拆箱共享单元清单。按照从内到外的包装顺序，清单依次记录：专业仓库单元、分拣台单元（如有）、整个楼层单元。然后在相邻楼层之间建立显式的备货链——楼层 N 完成后，按反转顺序为楼层 N+1 提交备货请求。

为什么要反转？因为发货出仓时，外层单元（整个楼层）最先执行——它包含注意力模块等前置加工。如果外层工具没备好，整个楼层都无法开工。所以备货提交顺序应该是：先备外层（整个楼层）、再备分拣台、最后备内层（专业仓库）。原始清单是 [专业仓库, 分拣台, 楼层]，反转后变成 [楼层, 分拣台, 专业仓库]——这正是备货的最优提交顺序。

回传回执阶段的备货链与发货出仓镜像。回传从最后一个楼层向第一个楼层推进，每个楼层完成回传后为前一个楼层提前备货。

与另一个框架（TorchTitan）相比，VeOmni 的方案更灵活。它动态构建每个楼层的拆箱共享单元清单，自动适配不同模型架构——无论楼层内部有多少独立单元，备货链都能正确建立。硬编码方案更高效但适配新模型时需要修改。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 拆箱共享单元清单 | _fsdp_modules 列表 |
| 显式备货链 | set_modules_to_forward_prefetch / backward_prefetch |
| 反转顺序 | reversed(_fsdp_modules) |
| 传送带空转 | all-gather 延迟导致的计算等待 |
| 备货窗口 | 通信-计算重叠的时间窗口 |

**三条要点**：

- 分仓制使每个楼层产生多个拆箱共享单元，隐式备货链因跨版图边界而断裂
- 备货提交顺序必须反转——先备外层（整个楼层），后备内层（专业仓库），因为外层加工先启动
- 动态构建单元清单的方案比硬编码更灵活，能自动适配不同模型的楼层结构

### D.12 库存快照：分仓参数的保存与恢复

**结论先行**：库存快照的保存需要在拆箱共享制的标签信息之上追加分仓维度的标签，恢复时则需要先剥离分仓标签再交给拆箱共享制处理——优化器记账簿还需要三处热插拔改装才能正确处理分仓参数。

**物流解释**：

训练中的专业仓库工具同时带有两层物流标签：内层标签记录"我的哪个切片在哪个拆箱共享站点"，外层标签记录"我属于哪个分仓组的哪些仓库"。但拆箱共享制在做库存快照时只看得到自己的标签——它不知道这些工具还被分仓制管理着。这就好比仓储管理系统记录了"货架 A 第三格存放了工具的第二片"，但没有记录"这些工具只是全网 128 个仓库中第 0 到 31 号仓库的"。恢复时，如果缺少分仓信息，系统无法判断该从快照中取哪一段数据放回哪个站点。

保存时的解决方案是通过快照钩子在快照生成后追加分仓标签。每一项被分仓制管理的工具，原本只带有拆箱共享制的一维物流标签（例如"按货架层切分"），钩子将其升级为二维物流标签（"按仓号切分"加"按货架层切分"），并将版图信息从一维拆箱共享版图扩展到二维分仓拆箱版图。这样快照里就完整记录了工具在分仓制和拆箱共享制两个维度上的分布信息。

恢复时的操作正好相反。快照中的工具带着二维物流标签（分仓加拆箱共享），但拆箱共享制的恢复逻辑只处理一维标签。恢复前的钩子把二维物流标签件还原为本地普通货物——通过提取当前站点对应的分仓切片，去掉分仓维度的标签。剩下的一维拆箱共享切分就交给拆箱共享制的标准恢复流程处理。

最棘手的是优化器记账簿。优化器为每个工具维护运行均值和方差等统计量，这些统计量的形状与工具完全一致，同样需要分仓感知。但拆箱共享制的优化器序列化逻辑深深嵌入在内部实现中，没有公开的扩展点。VeOmni 通过三处热插拔改装解决了这个问题：第一处让序列化逻辑跳过对分仓参数的标准切片处理（因为这些参数的切片已由分仓制决定）；第二处在保存优化器状态后给统计量追加分仓标签；第三处在恢复优化器状态前剥离分仓标签。三处改装组合起来，让优化器记账簿的保存和恢复具备了分仓感知能力。

值得注意的是，第二条路径（FSDP2）使用了原生的分布式快照机制，天然支持多维物流标签件，不需要这些热插拔改装。这也反映了两条路径的设计哲学差异：第一条路径通过改装补齐缺失的能力，第二条路径依赖平台原生支持。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 快照钩子 | state_dict_post_hook / load_state_dict_pre_hook |
| 二维物流标签 | DTensor with [Shard(0), Shard(1)] placements |
| 一维物流标签 | DTensor with [Shard(1)] placement |
| 优化器记账簿 | optimizer state (exp_avg, exp_avg_sq) |
| 三处热插拔改装 | 三个 monkey-patch |
| 分布式快照机制 | DCP (Distributed Checkpoint) |

**三条要点**：

- 保存快照时通过钩子追加分仓维度标签，恢复时先剥离分仓标签再交给拆箱共享制处理
- 优化器记账簿需要三处热插拔改装：跳过标准切片、保存后追加标签、恢复前剥离标签
- 第二条路径原生支持多维物流标签件，不需要这些热插拔改装

### D.13 全网实战：128 仓 16 站点的部署推演

**结论先行**：以 128 个专业仓库分布在 16 个站点的实际部署为例，每个站点持有 32 个仓库的工具切片，单站点专业仓库工具占用约 4.5 GB，每个楼层的通信总量约 557 MB。

**物流解释**：

网络规模是 16 个站点、128 个专业仓库、48 个楼层，每个包裹需要送往 8 个仓库加工。分仓组数为 4，拆箱共享组规模也是 4，合计正好覆盖 16 个站点。

版图布局采用就近分仓策略。16 个站点被排成 4 行 4 列的矩阵——行代表分仓组（同一行的 4 个站点持有相同的仓库子集），列代表拆箱共享组（同一列的 4 个站点共享同一仓库工具的不同切片）。例如站点 0、4、8、12 构成第一个拆箱共享组，它们共同持有仓库 E0 到 E31 的工具，每个站点存储工具的四分之一切片。

分仓切分的数值：每个仓库的入口加工工具原始尺寸为 [128 仓, 1024 宽, 2048 深]。按仓号切分后，每个站点只持有 32 个仓库的工具，变为 [32, 1024, 2048]。拆箱共享制再沿货架层方向切分（按第二维度四等分），最终每个站点存放 [32, 256, 2048]。三类工具加在一起，单站点每楼层约 96 MB，48 个楼层累计约 4.5 GB。

通信量方面，每个楼层有三项主要通信。第一项是干线互发发车：4096 个包裹各选 8 个仓库，分散到 4 组站点，每次通信约 128 MB。第二项是干线互发回车，通信量与发车相同。第三项是拆箱共享制的合并清单：每个站点需要从拆箱共享组的另外 3 个站点收集工具切片，约 301 MB。三项合计每楼层约 557 MB，48 个楼层的总通信量约 26 GB。

对账除数验证：系统设定对账除数为 16（全网站点数）。专业仓库的对账后分摊在 4 个站点间执行，除以 16 后得到全局均值——正确。如果不修正，默认除以 4，结果偏大四倍——错误。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 就近分仓 | ep_inside 布局策略 |
| 4 行 4 列矩阵 | ep_fsdp_device_mesh (4, 4) |
| 每站 32 仓 | 128 experts / ep_size 4 = 32 experts/rank |
| 96 MB/楼层 | 专家参数 per layer per GPU (bf16) |
| 26 GB 总通信 | 48 layers 的累计通信量 |

**三条要点**：

- 128 个仓库按仓号分成 4 组后，每站持有 32 个仓库的工具，再经拆箱共享制切分后单站约 4.5 GB
- 每楼层通信由三部分构成：发车干线互发、回车干线互发、拆箱共享合并清单，合计约 557 MB
- 对账除数设为 16 而非 4，是保证退货差异单全局正确性的关键

### D.14 总结：五大设计与三方对比

**结论先行**：VeOmni 的分仓拆箱共享体系建立在五个核心设计之上——声明式分仓配送单、独立的分仓版图、双层拆箱包装、退货差异单对账修正、以及库存快照扩展——它在复用现有模型生态的前提下实现了完整的分仓协同能力。

**物流解释**：

第一个设计是声明式分仓配送单。只需 16 行配置就能指定"哪些工具按仓号切分"，而不需要改动物流大楼（模型定义）本身的任何结构。这得益于热插拔改装机制——系统在运行时把原始的模块替换为支持三维工具矩阵的版本，然后按配送单的指示进行切分。适配一个新模型只需编写一份新的配送单。

第二个设计是独立的分仓版图。分仓拆箱版图是一张二维地图，行维度是分仓组（不同站点持有不同仓库），列维度是拆箱共享组（同一仓库工具在不同站点间共享切片）。这张版图与普通货物的全网拆箱共享版图完全独立——同一批站点，两种分组逻辑互不干扰。

第三个设计是双层拆箱包装。专业仓库模块先在分仓拆箱版图上做内层拆箱共享包装，然后整个楼层在全网版图上做外层拆箱共享包装，并通过免重复入库清单把专业仓库排除在外层管辖之外。两层包装让两种货物各自在正确的版图上被管理。

第四个设计是退货差异单的对账修正。由于专业仓库的拆箱共享组规模小于全网站点数，必须修正对账除数以确保退货差异单代表全局均值。退货差异单封顶也需要两步合并来获取全局范数。

第五个设计是库存快照扩展。通过快照钩子和热插拔改装，让模型工具和优化器记账簿的保存与恢复具备分仓感知能力。

三方对比方面，VeOmni 的独特优势在于复用现有模型生态——通过热插拔改装注入能力，无需重写模型。TorchTitan 走自定义模型路线，提供更多并行策略选择（包括特快专线后端和双线调度），但适配新模型需要编写完整的专业仓库组实现。第三方（Megatron 风格）不使用拆箱共享制，采用自定义的承运合同分组管理通信，在极大规模部署上更成熟但灵活性较低。三套方案在独立版图设计、双层包装结构上殊途同归，核心差异在于模型适配方式和支持的并行维度组合。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 声明式分仓配送单 | ParallelPlan（16 行配置） |
| 热插拔改装 | monkey-patch |
| 免重复入库清单 | ignored_states |
| 双层拆箱包装 | 内层 fully_shard(experts) + 外层 fully_shard(layer) |
| 三方对比 | VeOmni vs TorchTitan vs Automodel (Megatron-style) |

**三条要点**：

- 声明式分仓配送单让适配新模型的工作量降到 16 行配置，核心能力通过热插拔改装注入
- 五大设计（配送单、独立版图、双层包装、对账修正、快照扩展）缺一不可，共同构成完整的分仓拆箱协同体系
- 三个框架在核心架构上趋同（独立版图、双层包装），差异在于模型适配方式和并行维度组合的丰富程度

| Reduce-Scatter | 对账后分摊 | 先求和再切分——全网退货差异单汇总后每站只保留自己负责的部分 |
| gradient_divide_factor | 对账除数修正 | 修正专业仓库的退货差异单除数，使其等于全网站点数而非拆箱共享组大小 |
| monkey-patch | 热插拔改装 | 运行时替换现有模块，不修改原始定义即可注入新能力 |
| state_dict hook | 快照钩子 | 在保存或恢复快照前后执行额外操作的回调机制 |
| optimizer state | 优化器记账簿 | 优化器为每个工具维护的运行均值和方差，形状与工具相同 |
| clip_grad_norm | 退货差异单封顶 | 当全网差异单总范数超过阈值时，等比缩小所有差异单 |
| ignored_states | 免重复入库清单 | 告诉外层拆箱共享制"这些工具已有内层管家，不要重复管理" |
| DTensor | 物流标签件 | 带有分布式元数据（版图信息和切分维度）的参数 |
| Prefetch | 提前备货 | 在当前楼层加工时，预先从各站点收集下一楼层的工具切片 |

## F. 常见误解纠正

**误解 1：** "专业仓库的退货差异单只需要在拆箱共享组内对账就够了。"
**纠正：** 拆箱共享组（4 个站点）只持有同一批仓库工具的不同切片，它们处理的是全网数据的不同子集。对账后分摊在 4 个站点间只得到了四分之一数据上的差异单均值，不是全局均值。必须将对账除数修正为全网站点数 16，否则退货差异单被低估四倍，工具的更新步长偏大。
**为什么容易错：** 习惯性认为"拆箱共享组内的对账后分摊已经完成了全部对账"，忽略了分仓制缩小了共享组的规模。

**误解 2：** "提前备货只需要备下一楼层的外层单元（整个楼层），内层单元（专业仓库）会被隐式备货覆盖。"
**纠正：** 隐式备货只能跨越同级别的拆箱共享单元边界。外层单元知道"下一个外层单元在哪"，但不知道下一楼层内部还有一个在不同版图上的内层单元。如果不显式备货内层单元，专业仓库的工具合并清单在开工时才发起，浪费了与上一楼层计算重叠的窗口，造成传送带空转。
**为什么容易错：** "FSDP 自动管理合并清单"的直觉适用于单层包装场景，但双层包装时跨版图的内层单元超出了隐式机制的感知范围。

**误解 3：** "库存快照保存时只要把工具的本地数据存下来就行了，物流标签信息不重要。"
**纠正：** 恢复快照时，系统需要知道"这块数据应该放到哪个站点的哪个位置"。如果只存本地数据而丢失了分仓维度的标签，恢复到不同数量站点的集群时就无法正确地重新切分。二维物流标签（分仓加拆箱共享）记录了完整的分布语义，是跨集群恢复的必要信息。
**为什么容易错：** 存储时只关注"数据本身"，忽略了分布式语义需要的元数据。

**误解 4：** "退货差异单封顶时，只要在全网做一次合并就能得到全局范数。"
**纠正：** 普通货物确实可以一次合并——因为它们的拆箱共享组就是全网。但专业仓库的差异单切片分布在两个正交的维度上：拆箱共享组内散着同一仓库工具的不同切片，分仓组内散着不同仓库的差异单。一次合并只能覆盖一个维度，必须两步合并（先拆箱共享组内，再分仓组间）才能得到全局范数。
**为什么容易错：** "全局范数"暗示一个全局操作就够了，忽略了两个维度的正交性。

**误解 5：** "声明式分仓配送单意味着零改动就能适配任何模型。"
**纠正：** 分仓配送单解决的是"哪些参数按仓号切分"的声明问题，但前提是模型的专业仓库工具已经被改造为三维矩阵格式（[仓库数, 宽, 深]）。原始模型通常为每个仓库创建独立的工具，必须先通过热插拔改装把它们合并成三维矩阵，才能沿仓号维度切分。配送单是"零改动声明切分"，但热插拔改装是必要前提。
**为什么容易错：** "16 行配置"的简洁性掩盖了底层热插拔改装的存在。

**误解 6：** "第二条路径不需要任何分仓相关的特殊处理，完全靠原生机制自动搞定。"
**纠正：** 第二条路径确实省去了库存快照的热插拔改装（因为原生分布式快照机制支持多维物流标签件），但仍然需要：独立的分仓拆箱版图、双层拆箱包装、对账除数修正、两步差异单封顶、以及显式提前备货链。五大设计中只有第五个（快照扩展）被原生机制替代了，其余四个在两条路径上完全一致。
**为什么容易错：** "FSDP2 更先进"的笼统印象导致高估了原生支持的覆盖范围。

## G. 读者复述测试

**Q1（Why）：** 为什么对账除数修正的数值恰好等于分仓组数（而非其他数字）？请用 16 站点、4 组分仓的场景推导，并解释如果修正值偏大或偏小各会导致什么后果。

> **A：** 全网 16 个站点，专业仓库的拆箱共享组只有 4 个站点。拆箱共享制默认的对账除数是组内站点数 4，但正确值应该是全网站点数 16。差距倍数 = 16 / 4 = 4 = 分仓组数。所以修正量恰好是乘以分仓组数。如果修正值偏小（比如乘以 2 而非 4），退货差异单除以 8 而非 16，差异单偏大，工具更新步长过大，训练发散。如果修正值偏大（比如乘以 8），退货差异单除以 32，差异单偏小，工具更新步长过小，训练收敛变慢甚至停滞。修正值与分仓组数一致是因为 world_size = ep_fsdp_size * ep_size 的数学关系。

**Q2（What-if）：** 如果取消提前备货链，改为让每个楼层在开工前临时发起合并清单请求，在 48 个楼层的场景下大约会损失多少性能？为什么损失不是线性的？

> **A：** 没有提前备货时，每个楼层开工前必须等待合并清单完成（约 301 MB 的通信延迟），加上专业仓库的合并清单也被延迟。48 个楼层每层都增加一段等待时间，总延迟大致等于 48 次合并清单通信时间之和。但损失不是严格线性的，原因有二：第一，实际中并非所有楼层都是 MoE 楼层（部分楼层可能是普通楼层，只有一个拆箱共享单元，隐式备货仍然生效）；第二，合并清单与计算的重叠程度取决于计算量和通信量的比值——如果某一楼层的计算时间远长于通信时间，即使没有提前备货，合并清单也可能在计算期间自然完成，损失趋近于零。关键瓶颈出现在计算量小但通信量大的楼层。

**Q3（How）：** 在保存库存快照时，快照钩子如何区分哪些工具需要追加分仓标签、哪些不需要？这个判断依据从何而来？

> **A：** 快照钩子查阅分仓配送单生成的映射表（参数全限定名到分仓标签的字典）。如果某个工具的全限定名出现在映射表中，且其标签类型为"按仓号切分"，就需要追加分仓标签。不在映射表中的工具——比如注意力层的工具、归一化层的工具、分拣台的工具——都不需要追加。映射表在系统初始化时由分仓配送单的执行过程生成，并传递给快照扩展模块。整个链条是：配送单声明 -> 执行时建立映射表 -> 注册到快照钩子 -> 保存时逐项查阅。

**Q4（Why）：** VeOmni 在退货差异单封顶时把参数分成三组（普通拆箱切片、分仓拆箱切片、未切分参数），为什么不能把三组混在一起用同一个合并操作？

> **A：** 三组参数分布在不同的承运合同分组上。普通拆箱切片分布在全网 16 个站点的拆箱共享组中，一次全网合并就能得到全局范数。分仓拆箱切片分布在拆箱共享组（4 个站点）和分仓组（4 个站点）两个正交维度上，需要两步合并。未切分参数不需要任何合并——它们在所有站点上是完整副本。如果把三组混在一起做同一个合并操作，要么合并范围对普通参数过窄（漏掉了部分站点的差异单），要么对分仓参数过宽（使用了错误的承运合同分组，得到无意义的结果），要么对未切分参数多此一举（做了不必要的通信）。分组处理是正确性的要求，不是优化。

**Q5（How）：** 用完整的物流术语描述一个包裹在 MoE 楼层中从发货出仓到回传回执的全路径，标注每一步涉及哪些通信操作和哪些版图。

> **A：** 包裹进入楼层后，先经过分拣台评分，选出 8 个目标仓库。然后进入排序环节，按目标仓库编号重新排列。接着是第一次干线互发（在分仓版图的分仓组内执行）——包裹从源站点发往持有对应仓库的站点。到达目的站点后，再次排序使每个仓库的包裹连续排列，随后进入批量加工环节（仓库工具已通过拆箱共享制的合并清单在分仓拆箱版图的拆箱共享组内收集完毕）。加工完成后，反向排序恢复原始顺序，执行第二次干线互发（同一分仓组内，拆分规则互换）——结果从仓库站点回到源站点。源站点将来自不同仓库的结果按路由权重加权求和。回传回执阶段，整个过程反转：退货差异单沿第二次干线互发的通道回流，经过仓库工具的反向加工（此时工具通过拆箱共享制的合并清单再次收集），再沿第一次干线互发的通道回到源站点。拆箱共享制的对账后分摊在分仓拆箱版图的拆箱共享组内执行，对账除数修正为全网站点数。
