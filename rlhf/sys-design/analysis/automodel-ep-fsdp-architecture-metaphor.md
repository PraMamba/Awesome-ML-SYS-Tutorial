# Automodel EP+FSDP 架构：一个物流网络的故事

> 本文是 [automodel-ep-fsdp-deep-dive.md](./automodel-ep-fsdp-deep-dive.md) 的科普改写版。全文用物流隐喻替代代码和技术术语。零代码，全物流世界观。

## A. TL;DR 故事

一家物流公司要为数百个站点（GPU）建立一套"专业分拣网络"（MoE）的运营体系。核心难题是：普通货物和专业仓库的货物，在物流版图上需要不同的分组方式，不能硬挤在同一张地图里。Automodel 的解决方案是画两张独立的物流版图——一张管普通件，一张管特殊件——然后按严格的四步编排（分段处理→分仓制→临时存单→拆箱共享）完成全网部署。在通信层面，它引入了特快专线（DeepEP）替代默认承运商（NCCL），把分拣和发车合成一步操作，大幅减少调度开销。整套设计的核心取舍是：用两张版图的管理复杂性，换来普通件与特殊件互不干扰的切分灵活性。

## C. 三层解释

### C.1 一句话版

这套系统用两张不同的物流地图分别管理普通货物和专业仓库的货物，让两类货物各走各的最优路线，互不干扰。

### C.2 一段话版

当一个物流网络既有普通货物，又有需要送到专业仓库（MoE 专家）的特殊件时，所有站点（GPU）的分组规则会产生冲突——普通件按"同款备货+拆箱分货"两个维度分组，特殊件按"内拆箱组+分仓数"两个维度分组。Automodel 的解决方案是：为同一批站点画两张物流版图（DeviceMesh），每张版图有独立的维度划分。然后按照"长清单分段→分仓制→临时存单→拆箱共享"的严格顺序，把模型的每一层都安排到对应的版图上运作。

### C.3 技术版

Automodel 为 MoE 训练场景设计了双物流版图（DeviceMesh）架构。普通件版图（world_mesh）是一张五维地图：中转段（PP）、同款备货（dp_replicate）、拆箱分货（dp_shard）、长清单分段（CP）、协作加工（TP），覆盖注意力层、归一化层和分拣规则（Gate）的参数。特殊件版图（moe_mesh）是一张三维地图：中转段（PP）、内拆箱组（ep_shard）、分仓数（EP），专门管理专业仓库的工具（专家权重）。

全网部署编排（parallelize_model）按严格的四步顺序执行：先做长清单分段处理（CP），再做分仓制切分（EP，沿维度 0 把专家分配到不同站点），接着设置临时存单（Activation Checkpointing），最后做拆箱共享制（FSDP）。拆箱共享本身又包含三重逻辑——专业仓库在特殊件版图内沿维度 1 做内层拆箱、通过免重复入库清单把专家参数排除在外层拆箱之外、整个楼层（Transformer Block）在普通件版图上做外层拆箱。

通信层面，专线仓库组（DeepEP 后端）使用装卸月台（Buffer）在园区传送带（NVLink）和跨城专线（RDMA）两个通道上同时操作，把分拣和发车融合成一步操作，减少调度开销。

## D. 逐章改写

### D.1 概述与定位——三大关键决策

**结论先行**：Automodel 做了三个关键决策：画两张物流版图、换用特快专线替代默认承运商、对拆箱共享制做精细化二次改造。

**物流解释**：

想象你经营一个覆盖数百站点的物流网络。网络里有两类货物——普通件（Dense 参数）和特殊件（MoE 专家参数）。普通件在所有站点上同款备货，用标准的拆箱共享制管理就够了。但特殊件不同：它们要送到专业仓库去处理，而专业仓库分散在不同站点上。

第一个决策是画两张物流版图。普通件有自己的分组规则（按数据并行和上下文并行来划分），特殊件也有自己的分组规则（按分仓数和内拆箱组来划分）。如果硬把这两种分组规则塞进同一张版图，维度会冲突——普通件需要"同款备货"和"拆箱分货"两个维度，特殊件需要"分仓制"和"内拆箱组"两个维度，而这四个维度对站点的分组方式是不同的。两张独立的版图彻底消除了这个冲突。

第二个决策是换承运商。默认承运商（NCCL）的干线互发（All-to-All）功能是通用的，但不够高效。Automodel 引入了特快专线（DeepEP），它能直接走跨城专线（RDMA），把分拣和发车合成一个操作，省去了中间倒手的步骤。

第三个决策是对拆箱共享制做精细化改造。标准的拆箱共享制把整个楼层的所有工具一视同仁地拆分。但在 MoE 场景中，专业仓库的工具已经被分仓制管理了，如果再被外层拆箱共享制重复管理，就会出现"两个管家管同一批货"的混乱。改造后的方案是：专业仓库的工具有独立的内层拆箱，然后通过一份"免重复入库清单"告诉外层拆箱"这些货我已经管了，你别碰"。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 普通件 | Dense 参数（Attention、LayerNorm、Gate） |
| 特殊件 | MoE 专家参数 |
| 物流版图 | DeviceMesh |
| 默认承运商 | NCCL |
| 特快专线 | DeepEP |
| 拆箱共享制精细化改造 | FSDP 二次开发 |

**三条要点**：

- 两张物流版图分别管理普通件和特殊件，避免分组维度冲突
- 特快专线替代默认承运商，把分拣和发车融合成一步，减少调度开销
- 拆箱共享制经过精细化改造，通过免重复入库清单避免两个管家管同一批货

### D.2 双物流版图架构

**结论先行**：调度管理总部为同一批站点绘制了两张不同的物流版图，让普通件和特殊件各走最优路线。

**物流解释**：

普通件版图（world_mesh）是一张五维地图。五个维度分别是：中转段（PP，流水线式接力处理）、同款备货（dp_replicate，多个站点存同样的货）、拆箱分货（dp_shard，把工具拆开分到不同站点存储）、长清单分段处理（CP，把超长的发货清单切成几段分给不同站点）、以及协作加工（TP，把一个大件拆开让多个工人协作处理）。

除了这五个基础维度之外，系统还创建了三个"扁平化分组"。想象一下，你有"同款备货"和"拆箱分货"两个维度，但某些调度任务只关心"数据并行"这个整体概念——不管你是同款备货还是拆箱分货，你都属于"数据并行"这个大组。扁平化分组就是把多个维度合并成一个，方便特定场景的调度。具体有三个：数据并行大组（用于数据加载分片）、拆箱分货+长清单联合组（用于参数切分的实际维度）、以及全数据并行组（用于损失值的全网对账）。

特殊件版图（moe_mesh）是一张独立的三维地图：中转段（PP）、内拆箱组（ep_shard）、分仓数（EP）。它和普通件版图覆盖的站点完全相同——同样的站点，但用完全不同的维度来划分分组。

内拆箱组的规模（ep_shard_size）是这样推算的：在数据并行和长清单处理构成的所有站点中，分仓制占用了 ep_size 个站点来放不同的专业仓库。剩下的站点构成了内拆箱组——这些站点上的专业仓库工具需要用拆箱共享制做进一步切分。

举个例子：假设有 8 个站点，分仓数为 4。那么 8 个站点中，每 4 个站点各自拥有一套不同的专业仓库子集（这就是分仓制）。剩下的 8÷4=2 个站点构成一个内拆箱组——这两个站点上的同一套专业仓库工具，还需要进一步做拆箱共享分存。在版图上看，分仓制把站点 {0,1,2,3} 和 {4,5,6,7} 分成两组，每组内的 4 个站点各持有不同的专业仓库。而内拆箱组则把 {0,4}、{1,5}、{2,6}、{3,7} 配对——每对站点上的专业仓库工具需要在两个站点间拆箱共享。

为什么不能只用一张版图？因为普通件按 (同款备货, 拆箱分货) 来组织，而特殊件按 (内拆箱组, 分仓数) 来组织。这两种分组逻辑在数学上不兼容——同一个站点在普通件视角下属于"拆箱分货第 3 组"，在特殊件视角下可能属于"分仓第 2 组、内拆箱第 1 组"。硬塞进同一张版图会导致维度含义冲突，拆箱共享制无法正确区分该沿哪个维度切分。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 普通件版图 | world_mesh (pp, dp_replicate, dp_shard, cp, tp) |
| 特殊件版图 | moe_mesh (pp, ep_shard, ep) |
| 扁平化分组 | _flatten 创建的子网格 (dp, dp_shard_cp, dp_cp) |
| 内拆箱组 | ep_shard 维度 |
| 内拆箱组规模 | ep_shard_size = dp_cp_size / ep_size |
| 版图管理总部 | FSDP2Manager |

**三条要点**：

- 普通件版图有五个维度，特殊件版图有三个维度，覆盖同一批站点但分组方式完全不同
- 内拆箱组的规模由"数据并行站点总数÷分仓数"推算而来，决定了专业仓库工具在分仓之后还需要几个站点来做拆箱共享
- 扁平化分组把多个维度合并成一个，方便特定场景（数据加载、参数切分、损失对账）的调度

### D.3 分仓制的实现

**结论先行**：分仓制把每个专业仓库的工具沿"仓库编号"维度切分，让每个站点只存一部分专业仓库，但分拣规则（Gate）保持全量不切。

**物流解释**：

分仓制的核心操作是：把专业仓库工具的第一个维度（仓库编号维度）切开，分配到不同站点上。如果总共有 64 个专业仓库、分仓数为 4，那每个站点只持有 16 个仓库的工具。这个切分通过物流标签件（DTensor）机制完成——普通的工具变成了带有物流标签的工具，标签上写着"我是沿维度 0 切分的，原件分布在这 4 个站点上"。之后要用到这批工具时，系统可以根据标签知道哪部分在哪个站点上。

分仓制有一个关键设计：**只切专业仓库的工具，不切分拣台**。分拣台（Gate/Router）的权重在所有站点上保持完整副本。为什么？因为每个站点都需要完整的分拣信息来决定包裹（Token）该发往哪个专业仓库。如果分拣台也被切分了，站点就无法判断某个包裹是否应该发给不在本站的仓库——它连该仓库的分拣评分都算不出来。

切分完成后，如果使用的是专线仓库组（DeepEP 后端），系统还会初始化一个包裹调度站（MoEFlexTokenDispatcher）。包裹调度站需要知道两件事：本站持有哪些专业仓库（比如 0 号到 15 号），以及分仓制的承运合同分组（ProcessGroup）信息——这样它才能知道该和谁通信来发送和接收包裹。

遍历模型的每一层时，系统找到所有包含专业分拣网络（MoE）的楼层，对其中的专业仓库子模块执行分仓切分。注意这个遍历只关注 MoE 楼层——普通楼层（纯 Dense）没有专业仓库，自然跳过。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 分仓制切分 | ExpertParallel ParallelStyle, Shard(0) |
| 物流标签件 | DTensor |
| 分拣台（不切分） | Gate/Router 权重全量保留 |
| 包裹调度站 | MoEFlexTokenDispatcher |
| 承运合同分组 | ProcessGroup (ep_mesh.get_group()) |

**三条要点**：

- 分仓制只切专业仓库的工具（沿仓库编号维度），不切分拣台——因为每个站点都需要完整的分拣信息
- 切分后的工具变成物流标签件，标签记录了分布信息，支持按需还原全量或提取本地切片
- 专线仓库组在分仓后还需要初始化包裹调度站，告诉它本站持有哪些仓库以及通信对象

### D.4 拆箱共享制二次开发的核心——三重逻辑

**结论先行**：拆箱共享制经过二次开发，实现了三重逻辑：专业仓库内层拆箱、免重复入库清单排除专家参数、楼层级外层拆箱。

**物流解释**：

这是整套系统最精妙的部分。标准的拆箱共享制只有一种操作方式：把一个楼层的所有工具拆开，分存到多个站点上。但在 MoE 场景下，专业仓库的工具已经被分仓制管理了——如果拆箱共享制不加区分地再拆一次，就会出现"两个管家管同一批货"的冲突。

**第一重：内层拆箱**。专业仓库的工具已经被分仓制沿维度 0（仓库编号）切过了。如果内拆箱组的规模大于 1（即在分仓之后还有多余的站点需要进一步分摊存储），系统会在特殊件版图的内拆箱组子网格上，沿维度 1（隐藏层维度）再切一刀。为什么是维度 1？因为维度 0 已经被分仓制占用了——仓库编号维度已经切过，不能再切。所以只能沿下一个维度（隐藏层维度，即工具的"宽度"）来继续分摊。打个比方：分仓制把 64 个仓库的工具箱按编号分给了 4 个站点，每个站点拿到 16 个工具箱。内层拆箱再把每个工具箱沿宽度方向劈成两半，让内拆箱组内的 2 个站点各存一半。这样每个站点的存储压力进一步减少。

**第二重：免重复入库清单**。现在专业仓库的工具已经有了自己的管家（内层拆箱），外层拆箱共享制在处理整个楼层时，必须跳过这些已被管理的工具。系统通过一份"免重复入库清单"（ignored_params）来实现：在对楼层做拆箱共享时，明确列出"这些参数已经被别的管家管了，不要重复入库"。如果没有这份清单，外层拆箱会把专业仓库的工具也按自己的规则再切一次——维度冲突、切分重叠，整个系统就乱套了。

值得注意的是，当内层拆箱已经被应用时（ep_shard_enabled），拆箱共享制框架会自动识别已经被包裹过的子模块，不需要手动排除。但如果只有分仓制没有内层拆箱（即分仓数已经等于数据并行度，不需要额外的拆箱共享），专业仓库的工具就没有被任何拆箱共享制包裹过——此时必须手动用免重复入库清单排除，否则外层拆箱会误把它们纳入管理。

**第三重：楼层级外层拆箱**。排除了专业仓库工具之后，楼层内剩下的所有工具——注意力模块、归一化层、分拣规则（Gate）的权重——由普通件版图上的拆箱共享制统一管理。这意味着一个楼层内有两套平行的拆箱共享制：专业仓库的工具走特殊件版图的内层拆箱，其他一切走普通件版图的外层拆箱。

除了楼层之外，词嵌入层（Embedding）和输出投影层（LM Head）也分别被拆箱共享制包裹。输出投影层还有一个特殊处理：如果配置要求高精度计算，它会使用全精度包装（FP32）而非轻量包装（BF16），以保证最终输出的数值准确性。

最外层，整个模型再被一次拆箱共享制包裹，形成了从外到内层层嵌套的管理结构。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 内层拆箱 | fully_shard(experts, ep_shard_mesh, Shard(1)) |
| 沿维度 1 切 | shard_placement_fn=Shard(1)，沿 hidden dim 切 |
| 免重复入库清单 | ignored_params |
| 外层拆箱 | fully_shard(block, fsdp_mesh, ignored_params) |
| 轻量包装 | BF16 混合精度 |
| 全精度包装 | FP32 精度 |

**三条要点**：

- 内层拆箱沿维度 1 切，因为维度 0 已被分仓制占用——两把刀切不同方向，互不干扰
- 免重复入库清单防止外层拆箱重复管理已被内层拆箱接管的专业仓库工具
- 一个楼层内有两套平行的拆箱共享制——特殊件版图管专业仓库工具，普通件版图管其余一切

### D.5 全网部署编排——严格的四步顺序

**结论先行**：全网部署编排按"长清单分段→分仓制→临时存单→拆箱共享"的严格顺序执行，每一步都依赖前一步的结果，顺序不能调换。

**物流解释**：

全网部署编排（parallelize_model）就像一个总调度员，按固定的四步把模型的每一层都安排到正确的站点和版图上。这四步的顺序有严格的因果依赖：

**第一步：长清单分段处理（CP）**。这一步设置长清单的分段方式，不改变任何工具的形状，只是在通信层面告诉系统"超长的发货清单要怎么分段"。它必须最先做，因为后面的临时存单和拆箱共享都会修改模块结构，一旦结构被改，长清单的分段设置就可能挂载到错误的位置。

**第二步：分仓制（EP）**。把专业仓库的工具转成物流标签件，沿维度 0 切分。它必须在拆箱共享之前做，因为拆箱共享的第一重逻辑（内层拆箱 Shard(1)）和第二重逻辑（免重复入库清单）都依赖分仓制的结果——如果你还没做分仓，怎么知道该沿维度 1 再切一刀？怎么知道哪些参数需要排除？

**第三步：临时存单（Activation Checkpointing）**。用一个"存单包裹"把每个楼层包起来，前向计算时不保存中间结果，反向计算时重新计算。它必须在分仓制之后（因为分仓制改变了模块内部结构），又必须在拆箱共享之前（因为拆箱共享不能处理已经被存单包裹修改过的模块结构——包裹顺序很重要，先存单再拆箱，不能反过来）。

**第四步：拆箱共享制（FSDP）**。最后做，因为它需要知道哪些参数被分仓制管理了（用于免重复入库清单），而且拆箱共享会改变参数的底层存储方式（把多个参数打包成一个扁平化的大箱子），之后就不能再做分仓切分了。

另外一个值得注意的设计：全网部署编排明确禁止了"拆箱协作加工"（TP）。原因是分仓制和协作加工的组合需要极其复杂的通信组管理。Automodel 选择不实现这个组合——如果模型需要协作加工，走另一条独立的代码路径。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 全网部署编排 | parallelize_model |
| 长清单分段处理 | Context Parallelism (CP) |
| 临时存单 | Activation Checkpointing |
| 分仓制 | Expert Parallelism (EP) |
| 拆箱共享制 | FSDP |
| 拆箱协作加工（被禁止） | TP，不与 MoE 并行器组合 |

**三条要点**：

- 四步顺序（CP→EP→AC→FSDP）有严格的因果依赖：每一步都依赖前一步的结果，调换顺序会导致切分冲突或结构错误
- 临时存单必须夹在分仓制和拆箱共享之间——包裹顺序决定了模块结构的层次
- 协作加工（TP）与分仓制的组合被明确禁止，因为管理两者的交叉通信组过于复杂

### D.6 特快专线通信后端——DeepEP

**结论先行**：Automodel 用特快专线（DeepEP）替代默认承运商（NCCL）的干线互发，通过装卸月台的双通道设计和融合发车/回车机制，大幅减少通信开销。

**物流解释**：

特快专线系统由四层组件构成，从底层到顶层依次是：

**第一层：装卸月台（Buffer）**。装卸月台是一块预先分配的通信缓冲区，相当于物流枢纽的装卸区——所有进出的包裹都要经过这里。整个系统只有一个装卸月台（全局单例），所有楼层的专业分拣网络共用同一个。月台有两个通道：一个走园区传送带（NVLink，同一台机器内部的高速通道），一个走跨城专线（RDMA，不同机器之间的高速直连）。系统分别计算两个通道需要的空间大小，确保月台足够大。

月台采用惰性分配策略：第一次使用时才分配，之后复用。只有当需要更大的月台时（比如新的通信任务需要更多空间），才会重新分配一个更大的。通过环境变量还可以控制分配给特快专线的计算资源数量（SM 数量），默认为 20 个——这意味着特快专线的通信操作会占用站点（GPU）上 20 个计算单元，和模型计算共享算力。

**第二层：融合发车与融合回车**。传统的发车过程分两步：先把包裹按目的地排序（permute），再执行干线互发（All-to-All）。融合发车把这两步合成一步操作。具体流程是：先调用装卸月台的布局计算功能，搞清楚每个站点要发多少包裹、走园区传送带还是跨城专线；然后一次性完成排序和发送。

融合发车和融合回车之间存在一个精妙的对称性。前向计算时，融合发车负责把包裹送到专业仓库，融合回车负责把处理结果收回来。反向计算（回传回执）时，方向恰好相反——融合发车的反向操作调用的是装卸月台的回车功能（因为要把梯度收回来），融合回车的反向操作调用的是发车功能（因为要把梯度发出去）。为什么？因为干线互发的反向传播本身就是一次反方向的干线互发。

**第三层：存根（Handle）机制**。每次发车时，装卸月台会产生一张存根票据。这张票据记录了通信布局的所有细节：哪些包裹发给了哪个站点、每个站点收到了多少包裹、用了哪条通道等等。回车时需要凭这张存根来操作——没有存根就不知道结果该发回哪个站点。存根在发车时产生，在回车时消费——用完即废。

**第四层：专线调度管理器与共享机制**。包裹调度站（MoEFlexTokenDispatcher）内部使用一个专线调度管理器（_DeepepManager）来实际执行发车和回车。关键设计：所有楼层的包裹调度站共享同一个专线调度管理器实例（类变量，全局共享）。这意味着所有楼层共用一个装卸月台和一套存根状态，减少了内存开销。但代价是：不同楼层不能同时进行通信——它们必须排队使用同一个管理器，因为存根状态是独占的。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 装卸月台 | DeepEP Buffer（全局单例通信缓冲区）[NEW] |
| 园区传送带通道 | NVLink 通信通道 |
| 跨城专线通道 | RDMA 通信通道 |
| 融合发车 | FusedDispatch（permute + all-to-all 融合）[NEW] |
| 融合回车 | FusedCombine（all-to-all + unpermute 融合）[NEW] |
| 存根票据 | Handle（通信布局记录） |
| 专线调度管理器 | _DeepepManager（共享单例）[NEW] |

**三条要点**：

- 装卸月台有两个通道（园区传送带 + 跨城专线），按通信距离自动选择通道，全系统只有一个月台实例
- 融合发车/回车把分拣和干线互发合成一步，且前向和反向操作形成精确对称（发车的反向是回车，回车的反向是发车）
- 所有楼层共享同一个专线调度管理器，节省内存但排斥并行通信——一次只能有一个楼层在发车/回车

### D.7 两种专业仓库组实现的对比

**结论先行**：Automodel 提供标准仓库组和专线仓库组两种实现方式——前者用合并清单+对账后分摊通信，后者用特快专线的融合发车+批量加工，两者在通信方式、计算方式和适用场景上有根本区别。

**物流解释**：

**标准仓库组**的工作流程是经典的"先集齐、再加工、最后分发"模式。发车阶段，每个站点先把自己的包裹广播给分仓组内的所有站点（合并清单 All-Gather），这样每个站点都有了全部包裹的副本。然后每个站点只加工分配给自己的那些仓库的包裹——虽然拿到了全部包裹，但只处理自己负责的那部分。处理完后，结果通过对账后分摊（Reduce-Scatter）操作发回给原始站点。

这种方式的优点是简单直观，使用物流标签件（DTensor）的标准语义就能完成通信。缺点是通信和计算完全分离——先通信完才能开始计算——而且合并清单操作会让每个站点临时持有全量包裹，增加存储压力。计算方面，标准仓库组对每个专业仓库逐个循环处理，虽然可以通过流程优化师（torch.compile）加速，但本质上是串行的。

**专线仓库组**的工作流程完全不同。它不做合并清单，而是用融合发车直接把每个包裹点对点地发送到它该去的专业仓库所在的站点。这意味着每个站点只收到自己需要处理的包裹——没有冗余数据。计算方面，专线仓库组使用批量加工（grouped_gemm）一次性处理所有本地专业仓库的包裹，不需要逐仓库循环。处理完后，融合回车把结果发回原始站点。

两种实现都必须处理一个特殊情况：空仓库。如果某个站点上的某个专业仓库没有收到任何包裹（路由没有把任何包裹分给它），仓库的工具就没有参与前向计算，梯度无法流过。两种实现都用"虚拟加工"（dummy 计算）来解决——用一个全零的输入做一次象征性的计算，确保梯度通路不断裂。这就像即使仓库今天没有订单，管理员也要做一次"空运转"来保持设备运行状态。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 标准仓库组 | GroupedExperts |
| 专线仓库组 | GroupedExpertsDeepEP |
| 合并清单 + 对账后分摊 | All-Gather + Reduce-Scatter |
| 融合发车 + 批量加工 | FusedDispatch + grouped_gemm |
| 逐仓库循环加工 | for 循环逐专家计算 |
| 批量加工 | grouped_gemm（批量矩阵乘）[NEW] |
| 虚拟加工 | dummy 计算（保证梯度流） |

**三条要点**：

- 标准仓库组"先集齐再加工"（合并清单→逐仓循环→对账后分摊），通信和计算分离，适合调试和小规模场景
- 专线仓库组"点对点派送+批量加工"（融合发车→批量矩阵乘→融合回车），通信和排列融合，适合大规模多机训练
- 两种实现都用虚拟加工处理空仓库，确保梯度通路不断裂

### D.8 清单格式转换——Triton 高速分拣机

**结论先行**：特快专线返回的路由信息是"清单格式"（每个包裹选了哪几个仓库），但排列操作需要"全标格式"（每个包裹对每个仓库标 0 或 1），系统用高速分拣机（Triton kernel）在两种格式间高效转换。

**物流解释**：

这是一个容易被忽视但至关重要的数据格式问题。当特快专线完成发车后，返回的路由信息告诉你"第 1 个包裹选了仓库 0 和仓库 1，第 2 个包裹选了仓库 1 和仓库 2"。这是清单格式——紧凑，但不方便做排列操作。排列操作需要全标格式："第 1 个包裹，仓库 0 标 1、仓库 1 标 1、仓库 2 标 0、仓库 3 标 0；第 2 个包裹，仓库 0 标 0、仓库 1 标 1、仓库 2 标 1、仓库 3 标 0"。

转换过程由一台高速分拣机（Triton kernel）完成。分拣机对每个包裹做一件事：初始化一行全零的标记，然后在包裹选中的那几个仓库位置写入 1 和对应的分拣评分。同时还生成一张位置映射表——记录了全标格式中的每个位置对应清单格式中的第几个选择。这张映射表在反向计算时至关重要：回传回执（梯度）需要从全标格式转回清单格式，位置映射表指导了这个反向转换。

为什么不用普通的循环来做转换？因为每个包裹的转换操作完全独立——几千个包裹可以同时转换，高速分拣机利用站点（GPU）的大规模并行计算能力，一次性处理所有包裹，比逐个循环快几个数量级。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 清单格式 | indices 格式（每个 token 的 top-k 专家 ID）[NEW] |
| 全标格式 | multihot 格式（每个 token 对每个专家的 0/1 标记）[NEW] |
| 高速分拣机 | Triton kernel |
| 位置映射表 | position_map（反向转换用） |
| 清单格式转换 | indices ↔ multihot 转换 |

**三条要点**：

- 特快专线返回清单格式（紧凑），排列操作需要全标格式（展开），两者之间需要高效转换
- 高速分拣机利用大规模并行计算，同时处理所有包裹的格式转换
- 位置映射表是反向计算的关键：没有它，回传回执就无法从全标格式正确转回清单格式

### D.9 对账节奏控制——梯度同步与中转线适配

**结论先行**：MoE 场景下的对账（梯度同步）需要精确的节奏控制——在攒单期间禁用对账和重新摆货以节省通信开销，只在最后一车次才启用全量对账。

**物流解释**：

在训练过程中，如果攒单再对账（Gradient Accumulation）的步数大于 1，意味着系统要连续运行多个车次而只在最后一个车次做梯度同步。如果每个车次都做全网对账和重新摆货（reshard），通信开销会成倍增加——因为每次对账都是一次全网通信，每次摆货都是一次参数重新分配。

对账节奏控制器（MoEFSDPSyncMixin）的工作方式是：在攒单开始时，遍历所有被拆箱共享制管理的模块，把对账和重新摆货全部关闭。这包括普通模块（词嵌入、输出投影、模型主体）和专业仓库模块。关闭后，每个车次的反向计算只累积本地的退货差异单（梯度），不进行跨站同步。到了最后一个车次，控制器重新启用对账和摆货，让系统在这一次反向计算结束后执行全量梯度同步和参数重新分配。

当使用分段中转线（Pipeline Parallelism）时，情况变得更复杂。中转线把模型分成多段，每段放在不同的站点上，多个小车次（micro-batch）在段之间轮流穿梭。这带来一个新问题：每个小车次结束时都会触发反向计算，但不是每次反向计算都应该做梯度同步——只有整个攒单周期的最后一个小车次的反向计算才需要。

系统通过给标准中转线管理器打补丁来解决这个问题。补丁的逻辑是：每次反向计算前先禁用所有拆箱共享制模块的对账和摆货。反向计算完成后，检查两个条件：(1) 这是不是最后一个小车次的反向计算，(2) 下一步是不是优化器步骤（即真正的调库存账操作）。只有两个条件都满足时，才手动触发拆箱共享制的后处理——包括设置"最后一次反向"标志、启用对账和摆货、执行所有待处理的梯度同步和参数重新分配。

为什么 MoE 模块比普通模块多一个条件检查？因为在中转线中，每个小车次的最后一个反向计算不一定是全局最后一个。只有当这个反向计算后紧跟着优化器步骤时，才意味着所有小车次的梯度已经全部累积完毕，可以做同步了。系统用一个全局标志（IS_OPTIM_STEP）来传递这个信息，由训练循环在每个优化器步骤前后设置。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 对账节奏控制器 | MoEFSDPSyncMixin |
| 关闭对账和重新摆货 | set_requires_gradient_sync(False), set_reshard_after_backward(False) |
| 攒单再对账 | Gradient Accumulation |
| 重新摆货 | Reshard after backward |
| 分段中转线 | Pipeline Parallelism |
| 小车次 | Micro-batch |
| 调库存账 | Optimizer step |
| 最后一次反向标志 | IS_OPTIM_STEP 全局标志 |

**三条要点**：

- 攒单期间禁用对账和摆货，只在最后一个车次启用——省掉了中间车次的全网通信开销
- 中转线场景下需要额外的条件检查：不仅要是最后一个小车次，还要确认紧跟着优化器步骤，才触发对账
- 对账节奏控制器同时覆盖普通模块和专业仓库模块，确保全局行为一致

### D.10 库存快照与货品清单管理——检查点格式转换

**结论先行**：Automodel 的专业仓库工具在内部使用"合箱格式"存储，但外部标准（HuggingFace）使用"散件格式"，保存和加载检查点时必须在两种格式间双向转换，且必须感知物流标签件（DTensor）的分布状态。

**物流解释**：

专业仓库的工具在 Automodel 内部是"合箱"存储的：所有仓库的同类工具打包成一个大箱子。比如 64 个仓库的"上行工具"被打包成一个形状为 [64, dim, inter_dim] 的大箱子。但 HuggingFace 生态使用"散件"格式：每个仓库的每把工具单独存放，比如"仓库 0 的上行工具"、"仓库 0 的下行工具"、"仓库 1 的上行工具"等等。

**保存（合箱→散件）**：当保存库存快照时，系统需要把大箱子拆开。对于带门控的专业仓库，一个 [dim, 2×inter_dim] 的合并工具要拆成两把独立的工具（门控工具 [inter_dim, dim] 和上行工具 [inter_dim, dim]），同时做转置（因为两种格式的行列约定不同）。每把拆出来的工具还要标上正确的仓库编号——这个编号不一定是连续的，因为在分仓制下每个站点只持有部分仓库。

**加载（散件→合箱）**：方向相反。系统从散件格式中，只挑选属于本站点的仓库工具（通过分仓制的信息判断哪些仓库归自己管），跳过其他仓库的工具。收集齐本站所有仓库的工具后，把它们做转置、拼接、堆叠，合成一个大箱子。最后把大箱子转成物流标签件（DTensor），放到特殊件版图上，设置正确的分布语义：分仓维度沿维度 0 切分、内拆箱维度沿维度 1 切分、复制维度保持同步。

最精细的操作发生在"物流标签件感知的拆箱"中。当专业仓库工具是一个多维物流标签件（比如同时有分仓和内拆箱两层标签），把单个仓库的工具拆出来后，需要做三件事：(1) 从版图中移除分仓维度（因为单个仓库不再需要分仓切分）；(2) 调整所有切分维度的编号（因为维度 0 被移除了，原来沿维度 1 切的现在变成沿维度 0 切）；(3) 在剩余的版图上重新构造物流标签件。这确保了拆出来的单个仓库工具仍然有正确的分布标签——即使它只在内拆箱组内分布，标签也能正确反映这一点。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 合箱格式 | gate_and_up_projs / down_projs（合并存储） |
| 散件格式 | experts.{i}.gate_proj / up_proj / down_proj（HF 格式） |
| 库存快照 | Checkpoint |
| 货品清单 | State dict |
| 换箱贴标 | 格式转换（Native ↔ HuggingFace） |
| 物流标签件感知拆箱 | split_experts_weights_dtensor_aware |

**三条要点**：

- 内部合箱格式和外部散件格式的转换涉及拆箱/合箱、转置和重新编号，两种格式的行列约定不同
- 加载时只挑选属于本站点的仓库工具，跳过其他仓库——避免加载不需要的数据
- 物流标签件感知的拆箱必须在拆出单个仓库后调整版图维度和切分编号，确保分布语义不丢失

## F. 常见误解纠正

**误解 1：** "两张物流版图意味着需要两倍的站点"
**纠正：** 两张版图覆盖的是同一批站点。它们是同一群站点的两种不同分组方式——就像同一栋大楼，按功能分组是"研发部、市场部、财务部"，按楼层分组是"一楼、二楼、三楼"。站点数量不变，只是观察维度不同。
**为什么容易错：** "两张"暗示"两份"

**误解 2：** "内层拆箱切的是维度 0，和分仓制一样"
**纠正：** 内层拆箱切的是维度 1（隐藏层维度），不是维度 0。维度 0 已经被分仓制占用了（仓库编号维度）。两把刀切不同方向：分仓制切"哪些仓库归我"，内层拆箱切"每个仓库的工具我存哪一半"。如果两刀切同一个方向，工具箱的仓库编号维度会被切两次，每个站点只剩下极少数仓库的极小碎片，丧失了 MoE 的并行效率。
**为什么容易错：** "拆箱"联想到相同操作

**误解 3：** "分拣台（Gate）也被分仓制切分了"
**纠正：** 分拣台在所有站点上保持完整副本，不做任何切分。每个站点都需要完整的分拣评分来判断包裹该去哪个仓库——包括那些不在本站的仓库。如果分拣台被切了，站点只能看到部分仓库的评分，无法做出全局最优的路由决策。
**为什么容易错：** "专家相关"误判为都要切

**误解 4：** "所有楼层可以同时使用特快专线发车"
**纠正：** 所有楼层共享同一个专线调度管理器和同一个装卸月台。管理器内部维护着一份存根状态，这个状态是独占的——一个楼层在发车时，存根被这个楼层占用，其他楼层必须等它回车完毕、存根释放后才能使用。代价是吞吐受限，换来的好处是内存开销大幅减少（只需要一份装卸月台的内存，而非每层一份）。
**为什么容易错：** "共享"误读为"并行"

**误解 5：** "梯度攒单时每个车次都不做任何通信"
**纠正：** 攒单期间禁用的是对账（梯度同步）和重新摆货（reshard），但前向计算中的通信（如分仓制的干线互发、分拣台的路由计算）仍然正常进行。被跳过的仅仅是反向计算结束后的全网梯度对账和参数重新分配。这就像物流网络在攒单期间照常收发货，只是推迟了月底的全网对账。
**为什么容易错：** "禁用通信"范围过度泛化

**误解 6：** "合箱格式和散件格式只是命名不同，数据一样"
**纠正：** 两种格式的数据布局完全不同。合箱格式把多个仓库的同类工具堆叠成一个大矩阵，行列约定是 [dim, inter_dim]；散件格式把每个仓库的每把工具单独存放，行列约定是 [inter_dim, dim]（需要转置）。而且带门控的仓库在合箱格式中把两把工具拼在一起（[dim, 2×inter_dim]），散件格式中是分开的。转换不是简单的重命名，而是涉及拆分、转置和重组。
**为什么容易错：** "格式转换"听起来像是改名

**误解 7：** "四步编排顺序（CP→EP→AC→FSDP）是为了代码整洁才这样排的"
**纠正：** 这个顺序有严格的因果依赖。EP 必须在 FSDP 之前，因为 FSDP 的免重复入库清单依赖 EP 的结果；AC 必须在 FSDP 之前，因为 FSDP 不能处理被 AC 包裹修改过的模块结构；CP 必须最先做，因为后续步骤会修改模块结构。调换任意两步的顺序都会导致切分冲突或运行时错误。
**为什么容易错：** "编排"暗示可灵活调整

## G. 读者复述测试

**Q1（Why）：** 为什么专业仓库工具的内层拆箱沿维度 1 切而不是维度 0？如果强行沿维度 0 再切一刀会发生什么？

> **A：** 因为维度 0（仓库编号维度）已经被分仓制切过了。如果再沿维度 0 切，等于把仓库编号切了两次——原本每个站点持有 16 个仓库（64÷4），再切一次就变成 8 个，而另一个站点上的 8 个仓库是同一批仓库的重复碎片，违背了分仓制"不同站点持有不同仓库"的设计初衷。沿维度 1 切则是把每个仓库工具的"宽度"（hidden dim）劈开，不影响仓库的归属关系。

**Q2（What-if）：** 如果取消免重复入库清单（ignored_params），让外层拆箱共享制也管理专业仓库的工具，会出什么问题？

> **A：** 专业仓库工具会被两套拆箱共享制同时管理——内层拆箱在特殊件版图（moe_mesh）上沿维度 1 切，外层拆箱在普通件版图（world_mesh）上按默认维度切。两张版图的站点分组不同，两套切分规则冲突，导致同一个参数的不同碎片被分配到不一致的站点组上，梯度同步和参数收集都会得到错误的结果。

**Q3（How）：** 融合发车的反向计算为什么调用的是装卸月台的"回车"功能而不是"发车"功能？

> **A：** 因为干线互发（All-to-All）的反向传播本质上是反方向的干线互发。前向时融合发车把包裹从源站点发到目的站点；反向时需要把梯度从目的站点收回源站点，这正好是回车（combine）操作的语义。同理，融合回车的反向计算调用的是发车（dispatch）功能——把梯度从源站点再发到目的站点。前向和反向形成精确的对称关系。

**Q4（Why）：** 在中转线（Pipeline Parallelism）场景下，为什么 MoE 模块做对账时比普通模块多一个"是否紧跟优化器步骤"的条件检查？

> **A：** 因为在中转线中，多个小车次（micro-batch）轮流穿梭，每个小车次结束都会触发反向计算。最后一个小车次的反向计算只是"最后一个小车次"，不一定是"梯度已经积累完毕可以做同步"的时刻。只有当这个反向计算后紧跟着优化器步骤（调库存账），才意味着所有梯度已经攒齐，可以做全网对账。没有这个额外检查，系统可能在梯度还没攒完时就提前做了同步，导致参数更新不完整。

**Q5（How）：** 保存库存快照时，物流标签件感知的拆箱是如何处理"维度编号偏移"问题的？

> **A：** 当从一个多维物流标签件中拆出单个仓库的工具时，仓库编号维度（维度 0）被移除了。原本沿维度 1 切的内拆箱标签，现在应该变成沿维度 0 切——因为维度 0 消失后，所有更高编号的维度都要减 1。系统遍历所有切分标签，把每个标签的维度编号减 1（如果原编号大于 0），然后在移除了分仓维度的子版图上重新构造物流标签件。这保证了拆出来的单个仓库工具仍然有正确的分布语义。
