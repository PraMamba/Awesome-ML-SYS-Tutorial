# TorchTitan EP+FSDP：一个物流网络的故事

> 本文是 [TorchTitan EP+FSDP 深度源码分析](torchtitan-ep-fsdp-deep-dive.md) 的科普改写版。全文用物流隐喻替代代码和技术术语。零代码，全物流世界观。

## A. TL;DR 故事

一家超大型物流公司需要同时处理两种截然不同的货物——"普通件"走标准分拣线，"特殊件"必须经过专业分拣网络按类别派送到不同的专业仓库。问题在于，普通件和特殊件混在同一栋物流大楼的不同楼层，它们需要的物流版图、拆箱共享规则和备货节奏完全不同。TorchTitan 的解决方案是：为同一批站点绘制两张物流版图（普通件版图和特殊件版图），在专业仓库上实施双层拆箱共享制（内层按特殊件版图共享仓库工具，外层按普通件版图共享整层设备），并建立一套显式提前备货链来对抗清点等待造成的传送带停滞。核心洞察是——同一批站点可以根据不同货物类型，"变脸"成不同的物流组织形态，而关键是让两种形态在切换时不互相干扰。

## C. 三层解释

### C.1 一句话版

一家物流公司把普通件和特殊件混合处理的大楼改造成了"两张版图、双层拆箱、提前备货"的体系，让两种货物各走各的最优路线却共享同一批站点。

### C.2 一段话版

想象一栋物流大楼有几十个楼层，其中大部分楼层处理普通件（密集层），每隔几层出现一个特殊件处理中心（MoE 层）。普通件的站点之间通过"拆箱协作加工"（TP）和"拆箱共享制"（FSDP）来协同工作。但特殊件必须先经过分拣台按类别分流，然后用干线互发（all-to-all）把包裹送到对应的专业仓库，处理完再回车合并。这两种货物需要的物流版图不同、拆箱规则不同、通信方式不同。TorchTitan 的做法是：为同一批站点画两张版图（普通件版图和特殊件版图），在特殊件楼层实施双层拆箱，并建立显式的提前备货链来弥补干线互发中"清点等待"造成的备货中断。

### C.3 技术版

TorchTitan 为 Llama4 的交替 dense/MoE 架构设计了一套完整的多维度并行协同方案。核心挑战在于：普通件楼层（dense 层）工作在普通件版图（dense mesh，维度为 `[dp_replicate, fsdp, tp]`）上，特殊件楼层（MoE 层）工作在特殊件版图（sparse mesh，维度为 `[dp_replicate, efsdp, ep, etp]`）上，两者的站点分组方式不同。

系统提供四种分仓制策略：仅拆箱协作（TensorParallel）、标准分仓互发（ExpertParallel）、分仓加协作二维切分（ExpertTensorParallel）、以及特快专线分仓（DeepEPExpertParallel）。双层拆箱共享制让仓库工具在内层按特殊件版图共享、整层设备在外层按普通件版图共享。

关键性能瓶颈是分仓互发中的清点等待（D2H sync）——它阻塞传送带（CUDA stream），导致拆箱共享制的隐式提前备货失效。解决方案是建立显式备货链：每个楼层在完成自身工作后，主动为下一楼层提前备货。对于特殊件楼层，需要"双重备货"——同时预备整层设备和仓库工具。

全网部署编排严格按六步顺序执行：拆箱协作加工 → 分仓制部署 → 长清单分段处理 → 临时存单 → 流程优化师 → 拆箱共享制。顺序至关重要：每一步都依赖前一步的状态。

## D. 逐章改写

### D.1 全局挑战与解决方案

**结论先行**：一栋混合处理普通件和特殊件的物流大楼，面临版图不兼容、拆箱粒度不匹配、备货链断裂和优化编排冲突四大难题，TorchTitan 用七个模块逐一击破。

**物流解释**：

这栋物流大楼（Llama4 模型）采用交替设计——大部分楼层处理普通件（标准 FFN），每隔几层出现一个特殊件处理中心（MoE 层）。两类楼层在同一栋楼里共存，但它们需要的物流组织方式截然不同。

第一个难题是**版图不兼容**。普通件楼层按"普通件版图"组织站点：站点被分成若干"拆箱共享组"和"拆箱协作组"。特殊件楼层需要一张完全不同的"特殊件版图"：站点被重新分成"专业仓库分配组"（EP 组）、"特殊件拆箱共享组"（efsdp 组）和"特殊件协作组"（etp 组）。同一批站点，两张版图的分组方式不同。如果强行把特殊件塞进普通件的版图，仓库工具的切分维度就会对不上，因为普通件的工具按"隐藏层维度"切分，而特殊件的工具需要先按"专家维度"切分。

第二个难题是**拆箱粒度不匹配**。标准做法是以整个楼层为单位做拆箱共享，但特殊件楼层内部的标准仓库组需要在不同的版图上单独拆箱。这意味着一个楼层内部出现了两种拆箱规则——仓库工具用特殊件版图的规则，其余设备用普通件版图的规则。

第三个难题是**备货链断裂**。特殊件处理中心在干线互发前需要做清点等待（D2H sync），这个操作会阻塞传送带。传送带是先进先出的——前面的操作没完成，后面的操作无法提交。拆箱共享制原本会自动在传送带上插入"给下一楼层提前备货"的任务，但传送带被清点等待卡住后，备货任务也被一并阻塞了。结果是下一楼层开始工作时发现工具还没备好，只能干等。

第四个难题是**优化编排冲突**。流程优化师（torch.compile）需要把整个楼层的操作编排成一套固定方案，但特殊件楼层的拆箱共享钩子会打断优化编排的连续性（graph break），导致优化师只能对子模块逐个编排。

TorchTitan 用七个模块解决这些难题：四种分仓制策略提供灵活的专业仓库分配方式；双版图架构让普通件和特殊件各有自己的物流地图；双层拆箱共享制让仓库工具和楼层设备分别在不同版图上共享；显式备货链恢复被清点等待打断的提前备货；特快专线（DeepEP）提供高性能异步通信后端；双线调度（DualPipeV）让分段中转线和分仓互发的通信交织执行；子模块编排避免优化编排的断裂。

全网部署编排从一个入口函数开始，严格按六步顺序执行。这个顺序不能打乱——拆箱协作必须在拆箱共享之前完成，因为拆箱共享需要感知已经被切分过的工具；流程优化必须在临时存单之后、拆箱共享之前，以确保优化单元和拆箱单元对齐。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 物流大楼 | Transformer 模型 |
| 楼层 | Transformer 层 |
| 普通件楼层 | Dense 层 (标准 FFN) |
| 特殊件处理中心 | MoE 层 |
| 普通件版图 | Dense Mesh |
| 特殊件版图 | Sparse Mesh |
| 拆箱共享制 | FSDP |
| 分仓制 | Expert Parallelism |
| 清点等待 | D2H sync |
| 传送带 | CUDA stream |
| 全网部署编排 | parallelize_llama() |

**三条要点**：
- 普通件和特殊件共存于同一栋楼，却需要不同的物流版图和拆箱规则，强行统一会导致工具切分维度对不上。
- 清点等待阻塞传送带是整个系统的关键瓶颈——传送带是先进先出的，一旦堵住，后续所有备货任务都会延迟。
- 六步部署顺序是严格有序的链条：每一步都依赖前一步的结果，打乱顺序会导致后续步骤无法正确感知已切分的状态。

### D.2 大楼结构——交替楼层设计

**结论先行**：物流大楼通过一个"交替间隔"参数控制普通件楼层和特殊件楼层的出现频率，特殊件楼层内部由分拣台、排序器、标准仓库组和可选的公共加工区四大模块组成。

**物流解释**：

这栋物流大楼有几十个楼层。每个楼层在建设时会检查自己的编号——如果 `(楼层编号 + 1)` 能被交替间隔整除，这个楼层就是特殊件处理中心；否则就是普通件楼层。比如交替间隔为 4 时，第 3、7、11 层是特殊件楼层，其余是普通件楼层。

这个设计意味着部署编排不能"一刀切"——必须逐层判断每个楼层的类型，为它选择匹配的并行策略。

特殊件处理中心的内部结构如同一个精密的分拣网络。分拣台（Router）首先为每个包裹打分，决定把包裹送往哪几个专业仓库。标准仓库组（GroupedExperts）是核心处理单元，它的工具不是普通的平面工具，而是三维工具矩阵——第一维是"仓库编号"（分仓制在此维度切分），第二三维是工具的工作尺寸（拆箱协作在此维度切分）。排序器（TokenReorderer）把包裹按目标仓库重新排列，为批量加工做准备。公共加工区（shared_experts）处理所有包裹，不受分拣结果影响。

标准仓库组的三维工具矩阵有一个重要特性：在实际加工时，系统会把带物流标签（DTensor）的工具转换为普通工具。这是因为分仓互发的动态特性——每次送来的包裹数量不固定——与物流标签的自动通信语义冲突。物流标签适合固定模式的通信，但分仓互发中每个仓库收到的包裹数是动态的，需要精确手动控制。

分拣台使用"无辅助损失的负载均衡"机制：一个负载调节偏置（expert_bias）只影响分拣选择，不影响实际打分。换言之，偏置只改变"送往哪个仓库"的决定，不改变"这个仓库处理的权重"。这保证了在调节负载时不引入额外的训练噪音。

此外，特殊件处理中心可以选择在专业仓库加工之前就乘以分拣分数（score_before_experts），而不是加工之后再加权求和。前者与特快专线的异步回车合并配合更好——因为回车之后不需要再做额外加权。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 交替间隔 | interleave_moe_layer_step |
| 分拣台 | TokenChoiceTopKRouter |
| 排序器 | TokenReorderer |
| 标准仓库组 | GroupedExperts |
| 三维工具矩阵 | 3D 权重张量 (E, H, D) |
| 公共加工区 | shared_experts |
| 物流标签件 | DTensor |
| 负载调节偏置 | expert_bias |
| 分拣分数 | top_scores / gate values |

**三条要点**：
- 大楼的楼层交替排列普通件和特殊件处理中心，部署编排必须逐层判断类型。
- 标准仓库组的三维工具在实际使用时必须撕掉物流标签转为普通工具，因为分仓互发的动态包裹数与自动标签语义冲突。
- 负载调节偏置只影响分拣选择不影响加工权重——这是"无辅助损失负载均衡"的关键：调流量不调质量。

### D.3 物流版图设计——普通件版图 vs 特殊件版图

**结论先行**：调度员为同一批站点绘制了三张物流版图（数据装载、普通件、特殊件），通过一个核心公式 `efsdp = fsdp × tp ÷ (ep × etp)` 将普通件版图的维度重新映射到特殊件版图的维度空间。

**物流解释**：

所有站点（GPU）被组织进三张不同的物流版图，每张版图覆盖全部站点，只是分组方式不同：

第一张是**数据装载版图**，决定每个站点读取哪部分原始数据。第二张是**普通件版图**，用于所有普通件楼层的拆箱协作和拆箱共享。第三张是**特殊件版图**，用于特殊件楼层的分仓制和特殊件拆箱共享。

三张版图的设计必须满足一个硬约束：它们必须精确覆盖全部站点，不多不少。从普通件版图出发，总站点数等于各维度的乘积；从特殊件版图出发，总站点数也等于各维度的乘积。两者相等，消去公共维度后就得到了核心公式：特殊件拆箱共享维度（efsdp）= 普通件拆箱维度 × 协作维度 ÷ (分仓维度 × 特殊件协作维度)。

这个公式的物理含义是：普通件版图中用于拆箱共享和协作加工的站点资源，在特殊件版图中被重新分配给了分仓和特殊件协作。剩余的资源归给特殊件拆箱共享。如果分仓和特殊件协作"吃掉"了全部资源，特殊件拆箱共享维度就变成 1——但即便如此，特殊件的拆箱共享仍然存在，因为它还要负责混合精度中的工具格式转换（精度切换）。这就是为什么当分仓数大于 1 时，efsdp 维度在版图中始终保留的原因。

约束条件限制了两种模式：特殊件协作维度要么等于普通件协作维度（二维切分模式），要么等于 1（标准分仓模式）。前者意味着每个仓库的工具还要在协作组内进一步切分，后者意味着全部协作维度都让给了分仓和拆箱共享。

梯度除法因子跨越所有数据并行维度——无论工具在哪张版图上拆箱共享，梯度的平均计算都使用统一的全局因子。

以 8 个站点为例：普通件版图把站点分成 2 个拆箱共享组（每组 4 个站点做协作加工），特殊件版图把同样的站点分成 4 个分仓组。站点 0-3 在普通件眼中是一个协作组，在特殊件眼中是一个分仓组。站点 0 和 4 在普通件眼中是拆箱共享伙伴，在特殊件眼中也是特殊件拆箱共享伙伴。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 物流版图 | DeviceMesh |
| 普通件版图 | Dense Mesh [dp_replicate, fsdp, tp] |
| 特殊件版图 | Sparse Mesh [dp_replicate, efsdp, ep, etp] |
| 数据装载版图 | Dataloading Mesh |
| 特殊件拆箱共享维度 | efsdp |
| 分仓维度 | ep |
| 特殊件协作维度 | etp |
| 梯度除法因子 | fsdp_gradient_divide_factor |

**三条要点**：
- 三张版图覆盖全部站点，只是分组维度不同——同一批站点在不同版图中扮演不同角色。
- 核心公式 `efsdp = fsdp × tp ÷ (ep × etp)` 本质上是一个资源守恒方程：站点总数不变，只是维度分配方式变了。
- 即使特殊件拆箱共享维度为 1，拆箱共享仍然保留——因为它还要承担混合精度的工具格式转换职责。

### D.4 四种分仓制策略

**结论先行**：TorchTitan 提供四种分仓策略——仅协作加工、标准分仓互发、分仓加协作二维切分、特快专线分仓——通过统一接口实现灵活切换。

**物流解释**：

第一种策略是**仅拆箱协作加工**。当不启用分仓制时，所有专业仓库的工具只按隐藏层维度在协作组内切分，不做跨组分仓。每个协作组的站点拥有工具的完整副本（以专家维度计），输入包裹标记为"全员持有"，反向传播时标记为"需全员汇总"。

第二种策略是**标准分仓互发**。工具在专家维度（第一维）上切分——如果有 16 个专业仓库和 4 个分仓组，每组持有 4 个仓库的工具。包裹的发车和回车通过干线互发（all-to-all）完成，具体流程在下一章详述。

第三种策略是**分仓加协作二维切分**。工具同时在两个维度上切分：第一维按分仓组切分专家维度，第二维按协作组切分隐藏层维度。发车时需要两层处理：先在协作维度上标记输入为全员持有（反向时需汇总），再在分仓维度上执行标准干线互发。

第四种策略是**特快专线分仓**。工具切分方式与标准分仓相同（按专家维度切分），但发车和回车委托给特快专线后端（DeepEP），后者支持异步操作和通信-计算重叠。特快专线不兼容二维切分模式。

策略选择的决策逻辑是一棵决策树：先检查是否存在分仓版图——不存在则用纯协作加工；存在则检查是否启用特快专线——是则用特快专线分仓；否则检查是否存在特殊件协作维度——是则用二维切分，否则用标准分仓互发。如果启用了双线调度（DualPipeV），还会在选定策略外再包装一层同步钩子。

当分仓借用了全部协作维度（etp=1）时，协作组内的站点不再对仓库工具做协作切分，而是改为包裹级别的序列分片——每个站点只处理一部分包裹，最后再汇总。这需要排序器在输入输出上做分片和全局索引调整。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 仅拆箱协作加工 | TensorParallel (无 EP) |
| 标准分仓互发 | ExpertParallel (all-to-all) |
| 分仓加协作二维切分 | ExpertTensorParallel |
| 特快专线分仓 | DeepEPExpertParallel |
| 决策树 | apply_moe_ep_tp 策略选择逻辑 |
| 序列分片 | ReordererSequenceParallel |

**三条要点**：
- 四种策略的工具切分维度不同：纯协作只切隐藏层维度，标准分仓和特快专线只切专家维度，二维切分同时切两个维度。
- 策略选择是一棵确定性决策树，由版图配置唯一决定——不存在运行时的动态切换。
- 当分仓借用全部协作维度时，协作组内改为序列分片，每个站点只处理一部分包裹而非对工具做协作切分。

### D.5 发车派送与回车合并详解

**结论先行**：标准分仓互发的发车流程分四步——交换计数信息、计算发送/接收分配、主数据干线互发、从"按站点排列"重排为"按仓库排列"并对齐填充。

**物流解释**：

发车派送的第一步是**交换计数信息**。每个站点先统计自己有多少包裹要送给各个专业仓库，然后通过一次干线互发把这些计数信息发给所有相关站点。这样每个站点就知道自己将要收到多少包裹、来自哪些站点。

第二步是**计算发送/接收分配**。站点需要把计数信息从站点（GPU）搬到办公桌（CPU）上计算分配方案。这里有一个关键的清点等待——接收分配必须立即知道，因为站点需要根据它来准备接收空间。发送分配可以延迟计算（用异步清点），但接收分配必须同步等待。这个同步等待会阻塞传送带，是整个系统的性能瓶颈。为什么接收分配不能异步？因为站点必须先知道要接收多少包裹，才能分配接收缓冲区的大小——大小未知就无法开始接收。

第三步是**主数据干线互发**。根据计算好的分配方案，每个站点把包裹发往对应站点。这次互发支持自动微分——前向做正向互发，反向自动做反向互发。

第四步是**重排和对齐填充**。互发之后，包裹是按"来源站点"排列的——先是来自站点 0 的包裹，再是来自站点 1 的包裹，以此类推。但批量加工（grouped_mm）需要包裹按"目标仓库"排列——先是送给仓库 0 的所有包裹，再是送给仓库 1 的所有包裹。一个高速分拣机（Triton kernel）并行计算重排索引，同时在每个仓库的包裹末尾填充零值包裹，确保每个仓库的包裹数对齐到指定倍数。

对齐大小取决于加工精度：轻量包装（bf16）对齐到 8，压缩包装（fp8）对齐到 16，更高压缩（mxfp8）对齐到 32。对齐的目的是让批量加工操作能够高效利用硬件。

回车合并是发车的精确逆操作：先把包裹从"按仓库排列"反排回"按站点排列"（去掉填充），再做一次反向干线互发把加工结果送回原始站点。发送和接收的分配方案在回车时互换——发车时的发送量就是回车时的接收量。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 交换计数信息 | all_to_all(num_tokens_per_expert) |
| 清点等待 | D2H sync (non_blocking=False) |
| 主数据干线互发 | all_to_all_single_autograd |
| 高速分拣机 | Triton kernel (generate_permute_indices) |
| 对齐填充 | TOKEN_GROUP_ALIGN_SIZE_M padding |
| 批量加工 | grouped_mm |
| 反排 | _unpermute (scatter 回原位) |

**三条要点**：
- 发车的四步中，第二步的清点等待是唯一的同步阻塞点——接收分配必须同步获知，因为不知道大小就无法分配接收空间。
- 高速分拣机不仅重排包裹顺序，还在每个仓库末尾填充零值包裹做对齐——对齐倍数由加工精度决定。
- 回车合并是发车的精确镜像：先反排，再反向互发，发送/接收分配互换。

### D.6 双层拆箱共享制

**结论先行**：特殊件楼层需要双层拆箱共享——内层在特殊件版图的拆箱组上共享仓库工具，外层在普通件版图的拆箱组上共享整层设备——并通过条件切分维度和手动梯度除法解决版图不一致问题。

**物流解释**：

标准的拆箱共享制以整个楼层为单位，所有设备在普通件版图的拆箱组上共享。但特殊件楼层的标准仓库组已经被分仓制在专家维度上切分了，它的工具需要在特殊件版图的拆箱组上共享——这张版图的分组方式与普通件版图不同。

因此，特殊件楼层采用双层拆箱：
- **内层拆箱**：仓库工具（experts 的 w1/w2/w3）在特殊件版图的拆箱组（edp_mesh）上做拆箱共享。
- **外层拆箱**：整个楼层（包括注意力模块、分拣台、公共加工区等）在普通件版图的拆箱组（dp_mesh）上做拆箱共享。

内层必须先于外层完成包装——因为拆箱共享制是递归的，外层包装时会自动识别已被包装的子模块，不会重复切分。先包装仓库工具，再包装整个楼层，仓库工具就被识别为独立的拆箱单元。

有一个边界条件需要特殊处理：**条件切分维度**。分仓制已经在工具的第一维（专家维度）上切分了，如果"特殊件拆箱共享维度 × 分仓数"超过了专家总数，第一维上已经没有足够的切分空间。此时拆箱共享必须改为在第二维（隐藏层维度）上切分。举例：128 个仓库，8 路分仓，每站持有 16 个仓库的工具。如果特殊件拆箱维度为 4，4 × 8 = 32 < 128，第一维空间充足，继续在专家维度切分。但如果 efsdp 改成 16，16 × 8 = 128，恰好用完，此时再继续在第一维切分就没有余量了——需要切换到第二维。

最后，系统需要**禁用自动梯度除法**。因为内层和外层的拆箱组大小不同，各自的自动除法因子也不同。如果两层都各自除以自己的组大小，梯度会被除两次且因子不一致。解决方案是禁用所有拆箱共享单元的自动除法，在训练循环中用全局统一的因子手动除法。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 内层拆箱 | fully_shard(experts, edp_mesh) |
| 外层拆箱 | fully_shard(block, dp_mesh) |
| 特殊件拆箱组 | edp_mesh [dp_replicate, efsdp] |
| 普通件拆箱组 | dp_mesh [dp_replicate, fsdp] |
| 条件切分维度 | shard_placement_fn: Shard(0) vs Shard(1) |
| 禁用自动梯度除法 | disable_fsdp_gradient_division |

**三条要点**：
- 双层拆箱的顺序不可颠倒：必须先包装内层仓库工具，再包装外层整个楼层——因为拆箱共享制自动跳过已包装的子模块。
- 条件切分维度是一个边界处理：当"拆箱维度 × 分仓数"超过专家总数时，切分方向从专家维度切换到隐藏层维度。
- 禁用自动梯度除法后，系统用全局统一因子手动控制——确保无论工具在哪张版图上拆箱，梯度平均计算的分母一致。

### D.7 全链路提前备货策略

**结论先行**：分仓互发的清点等待会破坏拆箱共享制的隐式提前备货，TorchTitan 通过显式设置前向和反向的备货链（包括特殊件楼层的"双重备货"）来恢复通信-计算重叠。

**物流解释**：

拆箱共享制有一个精妙的隐式备货机制：当楼层 N 正在工作时，系统在同一条传送带上自动提交"给楼层 N+1 提前备货"的任务。传送带是先进先出的，所以备货任务会在楼层 N 工作完成后立即开始，不需要任何额外调度。到楼层 N+1 开始工作时，工具已经备好了。

但分仓互发引入了清点等待——传送带被迫暂停，等待站点把计数信息从站点搬到办公桌。在传送带暂停期间，系统本应自动提交的备货任务被卡住了——因为传送带是先进先出的，前面的操作没完成，后面的备货无法提交。结果是楼层 N+1 开始工作时，工具还没备好，只能空转等待。

解决方案是建立**显式备货链**。系统不再依赖隐式机制，而是手动指定每个楼层完成后应该为哪些模块备货。

前向备货链的规则是：
- 词嵌入层（入口）完成后，为第一个楼层备货。
- 每个楼层完成后，为下一个楼层备货。如果下一个楼层是特殊件处理中心，则需要"双重备货"——同时为整个楼层和仓库工具分别备货。因为特殊件楼层有两个独立的拆箱单元（外层整个楼层 + 内层仓库工具），两者的工具需要分别从各自的拆箱组收集。
- 最后一个楼层完成后，为输出层备货。

反向备货链是前向的镜像：输出层为最后一个楼层备货，每个楼层为前一个楼层备货（反向顺序），如果前一个是特殊件楼层则双重备货，最后一个楼层为词嵌入层备货。

备货的触发时机是确定的：当楼层 N 的前向计算完成后，拆箱共享制触发备货——从拆箱组中收集楼层 N+1 的全部工具。如果 N+1 是特殊件楼层，还要额外收集仓库工具。到楼层 N+1 开始前向时，工具要么已经备好（备货完成），要么正在路上（备货进行中但至少已提交），不会出现完全没有开始备货的情况。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 隐式提前备货 | FSDP implicit prefetch |
| 显式备货链 | set_modules_to_forward/backward_prefetch |
| 双重备货 | prefetch [block, block.moe.experts] |
| 备货触发 | FSDP all-gather 在 forward/backward 结束时提交 |

**三条要点**：
- 清点等待阻塞传送带后，隐式备货失效的原因是传送带的 FIFO 特性——前面的操作未完成，后面的备货任务无法提交。
- 特殊件楼层需要双重备货，因为它有两个独立的拆箱单元——外层整个楼层和内层仓库工具各自需要单独收集。
- 显式备货链是前向和反向各一条完整的链，覆盖从词嵌入到输出层的所有模块。

### D.8 特快专线后端详解

**结论先行**：特快专线（DeepEP）后端通过自定义操作注册实现临时存单（SAC）兼容，通过存根缓存桥接物流标签接口与非标签状态，通过异步回车合并加上手动同步实现通信-计算重叠。

**物流解释**：

特快专线后端涉及三个部门的协同：策略部门决定如何切分工具和包装发车/回车操作，通信部门负责实际的发车和回车执行，以及一个专用的特快专线版特殊件处理中心来编排重叠执行。

**自定义操作注册**：特快专线把发车和回车操作注册为系统级别的自定义操作。这样做有三个好处：第一，临时存单（SAC）机制需要知道哪些操作的结果需要保存、哪些可以重新计算——自定义操作可以被加入"需保存列表"；第二，流程优化师需要知道操作的签名才能正确追踪；第三，可以注册自定义的前向/反向实现。

**存根缓存机制**：特快专线的发车操作返回一个"票据"（handle），这个票据记录了通信状态。但系统的操作签名只支持标准包裹（Tensor），不支持非标准的票据对象。解决方案是把票据存入存根缓存，发车操作只返回一个存根编号。回车操作通过存根编号取出票据，完成回车后清除存根。在自动微分的上下文中，票据被保存到反向传播的上下文中，确保反向也能访问。

存根的生命周期是：发车前向时创建并缓存 → 发车上下文保存到自动微分 → 回车前向时从缓存取出 → 回车上下文时从缓存移除 → 反向时从自动微分上下文使用。

**反向的对称性**：发车的反向操作是回车（把梯度从仓库端收集回来），回车的反向操作是发车（把梯度分发到仓库端）。

**异步回车与手动同步**：特快专线的回车操作是异步完成的——它在通信传送带上提交回车任务后立即返回，不等待完成。返回的结果可能还没准备好。系统随后执行公共加工区的计算——这与回车的通信在不同传送带上并行进行。当需要使用回车结果时，调用手动同步操作等待通信完成。时序上：仓库加工 → 异步回车提交 → 公共加工区并行计算 → 手动同步 → 结果相加。

特快专线版的特殊件处理中心与标准版的关键差异：它不使用排序器（特快专线内部处理排序），它把更多参数传给仓库工具（包括分拣索引和分数），它的回车是异步的而非同步的。

**装卸月台管理**：特快专线使用预分配的装卸月台（Buffer），根据发车和回车的配置计算需要的园区传送带（NVLink）和跨城专线（RDMA）缓冲区大小。月台在通信组不变且大小足够时复用，避免重复分配。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 特快专线 | DeepEP |
| 自定义操作注册 | torch.library Op 注册 |
| 临时存单 | SAC (Selective Activation Checkpointing) |
| 存根/票据 | handle_cache + handle_id |
| 异步回车 | combine(async_finish=True) |
| 手动同步 | sync_combine() |
| 装卸月台 | Buffer (预分配通信缓冲区) |
| 通信传送带 | CUDA comm stream |

**三条要点**：
- 存根缓存机制解决了"非标准票据无法通过标准包裹接口传递"的问题——用编号代替实体，编号随自动微分上下文流转。
- 异步回车的价值在于让公共加工区的计算与回车通信并行进行——手动同步推迟到真正需要结果时才触发。
- 发车和回车在自动微分中互为反向——这是逻辑上的对称：正向的分发在反向时变成收集，正向的收集在反向时变成分发。

### D.9 流程优化师与特殊件楼层

**结论先行**：普通件楼层整层编排优化，特殊件楼层采用子模块级编排（跳过仓库工具以避免拆箱钩子打断编排），仓库的批量加工函数作为独立单元全局编排一次。

**物流解释**：

流程优化师（torch.compile）的目标是把重复的调度方案固化下来，避免每次运行都重新规划路线。但普通件楼层和特殊件楼层需要不同的编排策略。

对于普通件楼层，优化师可以把整个楼层的操作编排成一套固定方案——从注意力模块到普通办公区，一气呵成。

对于特殊件楼层，问题在于仓库工具被拆箱共享制独立包装了，拆箱共享的钩子（工具收集/归还钩子）会打断优化编排的连续性。如果强行编排整个楼层，临时存单（AC）会回退到完全非优化模式。因此，优化师对特殊件楼层采用子模块级编排：注意力模块单独编排，分拣台单独编排，公共加工区单独编排——唯独跳过仓库工具模块。

仓库工具虽然整体不编排，但其核心的批量加工函数作为全局函数被单独编排一次，所有楼层共享这个编排结果。当启用分仓制时，批量加工函数还需要特殊处理——标记输入包裹的第一维（数量维度）为"动态"，告诉优化师不要对这个维度做固定假设，因为干线互发后每个站点收到的包裹数量每次都不同。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 流程优化师 | torch.compile |
| 编排打断 | graph break |
| 子模块级编排 | per-submodule compile (跳过 experts) |
| 标记动态维度 | mark_dynamic(x, 0) |
| 临时存单 | Activation Checkpointing |

**三条要点**：
- 普通件楼层整层编排，特殊件楼层子模块逐个编排——差异源于拆箱共享钩子会打断编排的连续性。
- 仓库工具不整体编排，但其核心批量加工函数作为独立全局单元编排一次，所有楼层共享编排结果。
- 分仓互发后每站收到的包裹数量是动态的，必须标记为"动态维度"让优化师不做固定特化。

### D.10 双线调度——分段中转线与分仓互发的重叠

**结论先行**：双线调度（DualPipeV）通过同步钩子包装发车/回车操作，配合双线程栅栏和重叠回调，实现分段中转线的前向/反向两个线程与分仓互发通信的交织执行。

**物流解释**：

当分段中转线（PP）和分仓制（EP）同时启用时，存在两类通信：中转站之间的点对点交接（PP P2P send/recv），和专业仓库之间的干线互发（EP all-to-all）。这两类通信和计算之间可以交织——当一个中转段在等待干线互发完成时，另一个中转段可以执行计算。

双线调度的核心思想是用两个办公桌线程（CPU threads）交替在同一条传送带上提交任务。一个线程负责前向计算，另一个负责反向计算。它们通过四个同步钩子（标记为 A、B、C、D）协调：

- A 钩子：发车前同步——前向线程准备就绪，等待反向线程到达
- B 钩子：发车后同步——发车完成，两个线程交换执行权
- C 钩子：回车前同步——计算完成，等待对方到达
- D 钩子：回车后同步——回车完成，循环继续

每个同步点是一个双人栅栏——两个线程都到达后才一起继续。效果是干线互发通信和分段中转计算在传送带上交织排列。

关键设计细节：两个线程共享同一条传送带。这意味着它们不是真正的站点级并行（不是两个站点同时计算），而是办公桌线程级的交织提交——当一个线程在等待栅栏时（比如前向线程在等发车完成），另一个线程可以向传送带提交自己的任务。

栅栏协调器（HookCoordinator）管理栅栏的生命周期：启用时创建一个双人栅栏，计算特殊件楼层数量来确定交织的循环次数，超过次数后自动禁用协调。反向的第一个 D 钩子跳过栅栏以避免死锁（反向开始时只有一个线程活跃）。

双线调度与临时存单（AC）不兼容。原因是临时存单的重计算会重新执行前向，此时同步钩子的栅栏计数会混乱——重计算阶段没有对应的反向线程来配对栅栏，导致一个线程永远等不到另一个线程。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 双线调度 | DualPipeV |
| 同步钩子 (A/B/C/D) | SyncHook (autograd Function) |
| 双人栅栏 | threading.Barrier(2) |
| 栅栏协调器 | HookCoordinator |
| 办公桌线程交织 | 两个 CPU 线程共享同一 CUDA stream |

**三条要点**：
- 双线调度不是真正的站点级并行，而是两个办公桌线程在同一条传送带上交替提交任务——通过栅栏协调交织执行。
- 四个同步钩子（A→B→C→D）形成一个循环，每个钩子都是双人栅栏——两个线程都到达后才继续。
- 双线调度与临时存单不兼容，因为重计算会破坏栅栏的线程配对关系。

### D.11 全网部署编排的六步流程

**结论先行**：全网部署编排严格按"拆箱协作 → 分仓部署 → 长清单分段 → 临时存单 → 流程优化 → 拆箱共享"的顺序执行六步，每步的执行都依赖前一步的结果。

**物流解释**：

整个物流大楼的并行化部署从一个入口开始，按严格顺序执行六步，不可打乱：

**第一步：拆箱协作加工**。为非特殊件模块设置协作加工方案：词嵌入层、规范化层、输出层以及每个楼层的注意力模块和普通办公区。MoE 模块被跳过——由第二步处理。

**第二步：分仓制部署**。为特殊件楼层设置分仓方案。包括 MoE 层级的协作规则（分拣台不切分、公共加工区做协作切分）以及仓库工具的分仓/协作方案（根据策略决策树选择四种之一）。如果启用双线调度，在此步额外包装同步钩子。如果使用特快专线，在此步前完成初始化：导入特快专线模块以注册自定义操作，并把操作加入临时存单的保存列表。

**第三步：长清单分段处理**。如果启用上下文并行，为每个楼层的注意力模块设置长清单分段方案。

**第四步：临时存单**。如果启用激活检查点，为模型包装临时存单模块。这会用"临时存单包装器"包装每个楼层——前向时不保存中间结果（省空间），反向时重新计算。

**第五步：流程优化**。在临时存单之后、拆箱共享之前执行。优化师需要看到被临时存单包装后的模块结构，才能正确编排。而拆箱共享的钩子在特殊件楼层会打断编排，所以优化必须在拆箱共享之前完成。

**第六步：拆箱共享制**。最外层包装。先包装词嵌入，再逐层包装每个楼层（特殊件楼层先内层后外层），最后包装输出层和模型根。包装完成后禁用自动梯度除法，最后设置显式备货链。

**顺序依赖的因果链**：拆箱协作加工把工具切分为物流标签件，后续步骤需要感知这些标签；分仓制进一步在专家维度切分工具，拆箱共享需要知道已切分的维度才能正确选择切分方向；临时存单包装模块后改变了模块结构，流程优化需要看到包装后的结构；流程优化替换前向为编排版本后，拆箱共享在编排后的模块上注册钩子。任何打乱都会导致后续步骤看到错误的状态。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 全网部署编排 | parallelize_llama() |
| 拆箱协作加工 (Step 1) | apply_non_moe_tp() |
| 分仓制部署 (Step 2) | apply_moe_ep_tp() |
| 长清单分段处理 (Step 3) | apply_cp_to_attention() |
| 临时存单 (Step 4) | apply_ac() |
| 流程优化 (Step 5) | apply_compile() |
| 拆箱共享制 (Step 6) | apply_fsdp() |

**三条要点**：
- 六步顺序是严格的因果链：每步产生的状态是下一步的输入，打乱会导致下游步骤看到不一致的切分状态。
- 流程优化必须夹在临时存单和拆箱共享之间——太早看不到包装后的结构，太晚会被拆箱钩子打断编排。
- 特快专线的初始化必须在分仓部署之前完成——因为分仓部署时需要特快专线的自定义操作已注册。

### D.12 数值示例——三种站点配置

**结论先行**：通过三个具体的站点配置示例（8 站点仅协作、64 站点标准分仓、64 站点二维切分），展示普通件版图和特殊件版图的完整计算过程及站点分配方式。

**物流解释**：

**示例一：8 个站点，仅拆箱协作（无分仓制）**

配置：2 个拆箱共享组 × 每组 4 个协作站点。分仓数为 1，不启用分仓制。

普通件版图把 8 个站点分成 2 个拆箱共享组，每组 4 个站点做协作加工。站点 0-3 是一个协作组，站点 4-7 是一个协作组。拆箱共享在组间进行：站点 0 和站点 4 是拆箱共享伙伴。

由于不启用分仓制，特殊件版图的计算结果是 efsdp=8（所有资源都给了拆箱共享维度）。所有楼层使用纯协作加工策略，单层拆箱共享，隐式提前备货。

**示例二：64 个站点，标准分仓互发（EP=8，ETP=1）**

配置：8 个拆箱共享组 × 每组 8 个协作站点。分仓数为 8，标准分仓模式。

普通件版图把 64 个站点分成 8 个协作组，每组 8 站点。特殊件版图把同样的站点分成 8 个分仓组（每组恰好也是 8 个站点，与协作组占用相同的站点范围），特殊件拆箱共享维度 = 8 × 8 ÷ (1 × 8) = 8。

普通件楼层：站点 0-7 是一个协作组，站点 0, 8, 16, ..., 56 是一个拆箱共享组。

特殊件楼层：站点 0-7 是一个分仓组（每个站点持有总专家数的 1/8），站点 0, 8, 16, ..., 56 是一个特殊件拆箱共享组。

由于分仓借用了全部协作维度（etp=1），启用序列分片。双层拆箱共享——内层在特殊件拆箱组上，外层在普通件拆箱组上。显式备货链。

假设 128 个仓库：efsdp × ep = 8 × 8 = 64 < 128，第一维空间充足，使用默认的专家维度切分。

**示例三：64 个站点，分仓加协作二维切分（EP=8，ETP=8）**

配置与示例二相同的站点总数，但特殊件协作维度也设为 8。

特殊件版图：efsdp = 8 × 8 ÷ (8 × 8) = 1。分仓和特殊件协作吃掉了全部资源，特殊件拆箱共享维度降为 1——但拆箱共享仍然存在（负责混合精度转换）。

仓库工具同时在两个维度切分：分仓组切专家维度 8 份，协作组切隐藏层维度 8 份。实际上 EP 和 ETP 组合构成了 64 个站点的二维矩阵。

双层拆箱中内层拆箱组大小为 1，拆箱共享只负责格式转换，不做实际的数据并行切分。

**三个示例的对比**：从示例一到示例三，分仓制的参与度从 0 到最大。随着分仓数增加，特殊件拆箱共享维度从最大递减到 1。拆箱层数从单层变成双层。备货策略从隐式变成显式。通信模式从纯协作收发变成协作加干线互发再到干线互发加协作归约。

**隐喻对照**：

| 隐喻 | 技术概念 |
|------|----------|
| 8 站点配置 | pp=1, dp_shard=2, tp=4, ep=1 |
| 64 站点标准分仓 | pp=1, dp_shard=8, tp=8, ep=8, etp=1 |
| 64 站点二维切分 | pp=1, dp_shard=8, tp=8, ep=8, etp=8 |
| 特殊件拆箱共享维度降为 1 | efsdp=1, 仅负责混合精度 |

**三条要点**：
- 分仓数越大，特殊件拆箱共享维度越小——资源是守恒的，分给分仓的多了，留给拆箱的就少了。
- 即使拆箱共享维度降为 1，拆箱共享仍然保留其混合精度转换的职责。
- 三个示例展示了一个连续谱：从"全部资源给协作"到"全部资源给分仓+协作二维切分"，系统的复杂度和通信模式逐步升级。

## F. 常见误解纠正

**误解 1：** "普通件版图和特殊件版图使用不同的站点。"
**纠正：** 两张版图覆盖完全相同的全部站点，只是把同一批站点按不同维度分组。站点 0 在普通件版图中属于协作组 A，在特殊件版图中属于分仓组 B——是同一个站点在两张地图上的不同身份。
**为什么容易错：** "两张版图"让人直觉以为是两批不同的站点。

**误解 2：** "双层拆箱是因为特殊件楼层需要拆箱两次（先拆一半再拆另一半）。"
**纠正：** 双层拆箱是因为特殊件楼层内部有两个拆箱单元，它们分别在不同的版图上运作。内层仓库工具在特殊件版图上拆箱，外层整个楼层在普通件版图上拆箱。不是同一组东西拆两次，而是两组不同的东西各拆一次、用不同的规则。
**为什么容易错：** "双层"容易理解为"串行两次拆箱"。

**误解 3：** "清点等待阻塞了整个系统，所有站点都停下来了。"
**纠正：** 清点等待只阻塞了本站点的传送带。其他站点的传送带不受影响。但由于传送带是 FIFO 的，本站点传送带上排在清点等待后面的所有任务（包括提前备货）都被延迟了。破坏的是本站点的提前备货链，不是全网的计算。
**为什么容易错：** "阻塞"一词暗示全局性停滞。

**误解 4：** "双线调度让两个站点同时计算，实现了真正的并行。"
**纠正：** 双线调度让两个办公桌线程在同一条传送带上交替提交任务。传送带上的任务仍然按顺序执行。并行效果来自"当一个线程等待通信时，另一个线程可以提交计算任务"，是通信-计算的交织，不是两个站点同时处理。
**为什么容易错：** "两个线程"让人联想到真正的 GPU 并行。

**误解 5：** "六步部署顺序是为了代码整洁，调换顺序也能工作。"
**纠正：** 顺序是因果依赖决定的——拆箱协作在前是因为拆箱共享需要感知已切分的工具标签；流程优化夹在临时存单和拆箱共享中间是因为太早看不到临时存单包装、太晚会被拆箱钩子打断。打乱任何一步都会导致后续步骤看到错误的状态，产生静默的错误行为。
**为什么容易错：** 六步看起来像独立的"插件"。

**误解 6：** "特快专线（DeepEP）只是比标准干线互发更快的通信方式。"
**纠正：** 特快专线不仅更快，它的核心价值在于支持异步回车——回车操作提交后立即返回，不阻塞计算传送带。这让公共加工区的计算能与回车通信并行执行。标准干线互发的回车是同步的，必须等通信完成才能继续。速度只是表象，异步才是本质。
**为什么容易错：** "特快"暗示只是速度更快。

**误解 7：** "条件切分维度是一种优化，不用也能工作。"
**纠正：** 条件切分维度是一个必要的边界处理。当"拆箱共享维度 × 分仓数"超过专家总数时，专家维度上已经没有足够的切分空间。如果强行在专家维度切分，每份会小于一个完整的专家——这在逻辑上无意义。切换到隐藏层维度不是优化，而是正确性保障。
**为什么容易错：** "条件"一词让人以为是可选的优化路径。

## G. 读者复述测试

**Q1（Why）：** 为什么分仓互发中的清点等待会导致拆箱共享制的提前备货失效？如果不建立显式备货链，后果是什么？

> **A：** 清点等待（D2H sync）阻塞了传送带（CUDA stream），而传送带是先进先出的——前面的操作未完成，后面排队的提前备货任务无法提交。拆箱共享制的隐式备货原本依赖传送带的顺序执行自动插入备货任务，但清点等待把传送带卡住了，备货任务也被一并延迟。如果不建立显式备货链，下一楼层开始工作时会发现工具未就位，必须临时等待工具收集完成，造成计算空转，吞吐量下降。

**Q2（What-if）：** 如果打乱六步部署顺序，把拆箱共享制（第六步）提前到拆箱协作加工（第一步）之前执行，会发生什么？

> **A：** 拆箱共享制需要感知工具已被协作加工切分后的物流标签（DTensor placements）。如果先执行拆箱共享，它看到的工具还是未切分的完整工具，会按默认方式在第一维切分。随后协作加工再切分一次，两次切分的维度可能冲突，导致工具被重复切分或切分维度不一致。更严重的是，拆箱共享的梯度归约通信会使用错误的版图分组，产生静默的数值错误。

**Q3（How）：** 特快专线（DeepEP）后端如何实现公共加工区计算与回车通信的并行？请用物流术语描述完整的时序。

> **A：** 仓库加工完成后，特快专线在通信传送带上提交异步回车任务并立即返回——此时结果可能尚未到达。计算传送带随即开始执行公共加工区的加工。两条传送带并行运作：通信传送带上的回车与计算传送带上的公共加工区同时进行。当公共加工区完成后，系统调用手动同步（sync_combine），等待通信传送带上的回车也完成。最后，将公共加工区的结果与回车结果相加。关键在于"异步提交 + 延迟同步"——同步点被推迟到真正需要结果时。

**Q4（Why）：** 为什么双线调度（DualPipeV）与临时存单（Activation Checkpointing）不兼容？

> **A：** 双线调度依赖四个同步钩子（A/B/C/D）处的双人栅栏来协调前向线程和反向线程的交替执行。临时存单在反向时会触发重计算（重新执行前向），此时同步钩子再次被执行，但重计算阶段只有一个线程在运行（没有配对的反向线程），栅栏等待另一个线程永远不会到来——造成死锁。栅栏的设计假设"两个线程总是成对到达"，而临时存单的重计算打破了这个假设。

**Q5（How）：** 在一个 64 站点、8 路分仓（EP=8）、ETP=1 的配置中，当所有普通件和特殊件楼层同时工作时，同一个站点在普通件楼层和特殊件楼层分别扮演什么角色？它的通信模式有何不同？

> **A：** 在普通件楼层，该站点是 8 站点协作组中的一员（拆箱协作），通信模式是协作组内的合并清单（all-gather）和对账后分摊（reduce-scatter）。在特殊件楼层，同一站点变成了 8 站点分仓组中的一员，持有总专家数的 1/8，通信模式切换为干线互发（all-to-all）——每个站点把本地包裹按目标仓库发往对应站点，再从对应站点收回加工结果。同时，由于 ETP=1，该站点还参与序列分片——只处理一部分包裹的排序和索引调整。切换楼层时，站点的"身份"（属于哪个组）和"通信方式"（收发 vs 互发）都会改变，但物理位置不变。
